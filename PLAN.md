# Карта развития ChatGrab

Рабочий документ. Обновляется в конце каждой сессии — статусы, журнал, найденные
по дороге проблемы. Источник правды о том, что сделано и что предстоит.

---

## Как начинать сессию

Скажите одну фразу:

> Прочитай PLAN.md, начинаем сессию С<N>.

Я сверю состояние репозитория с этим файлом, назову, что осталось от прошлого
раза, и начну. В конце сессии обновлю статусы и журнал внизу.

Если хотите поменять порядок — скажите номер, порядок не догма. Зависимости
между сессиями отмечены в каждом разделе.

---

## Инварианты — держатся в каждой сессии

1. Приложение остаётся портативным: один `.exe`, без установщика и сервера.
2. Одна сессия — один коммит с описанием, зелёные тесты на Linux **и** Windows,
   собранный и запускающийся exe.
3. Изменение схемы БД — только через нумерованную миграцию, с бэкапом базы перед
   апгрейдом и тестом на копии.
4. Новая функция закрывается тестом. Смоук по экранам продолжает проходить.
5. Никаких командных функций: один человек, одна машина. Поле `owner` в лиде
   заполняется одним локальным значением — единственная уступка будущему.
6. Рассылка от юзербота — зона риска бана. Холодное первое сообщение по умолчанию
   готовится как черновик и уходит только по клику человека.
7. Мастер-пароль шифрует сессии, токены ботов и учётные данные интеграций.
8. Новая зависимость — только с обоснованием: каждая библиотека это вес exe и
   риск сборки.
9. Если задача требует переписать больше трёх модулей или сломать совместимость —
   останавливаюсь, описываю варианты, спрашиваю.

## С1. Фундамент миграций + справочник направлений

**Что меняется для менеджера:** появляется место, где заданы направления работы —
косметическое сырьё, АКБ, упаковка, пресс-формы, промхимия — с ключевыми словами
и файлом прайса. Дальше они подставляются в лиды, сценарии и фильтры.

**Почему вместе:** это одна и та же работа с БД, и справочник — первая проверка
нового механизма миграций на живом изменении.

### Миграции

- [ ] `db/migrations/` — нумерованные шаги `001_…`, `002_…`, каждый с `up` и,
      где обратим, `down`
- [ ] Существующая логика `migrate()` переносится в шаг `006_baseline` без
      изменения поведения — базы v6 продолжают открываться
- [ ] Обязательный бэкап базы перед апгрейдом схемы через `backup_service`,
      с записью в журнал: откуда, куда, какая версия
- [ ] Отдельная миграция откатывается на копии — `down` там, где он однострочный
      (добавленная колонка, новая таблица)
- [ ] Тест: копия базы v2 → апгрейд до текущей → проверка колонок и данных;
      расширяет существующий `tests/test_migration.py`

**Решение по откату:** полного набора `down` не пишем. Бэкап перед миграцией
откатывает и то, что в SQLite необратимо (удалённая колонка требует пересборки
таблицы). `down` пишем только там, где он однострочный.

### Справочник направлений

Плоский, без номенклатуры — пять направлений на одного человека не требуют
позиций и единиц измерения. Появятся, если окажутся нужны.

```sql
CREATE TABLE direction (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    keywords TEXT NOT NULL DEFAULT '[]',   -- для поиска в чатах и мониторинга
    stop_words TEXT NOT NULL DEFAULT '[]',
    price_file TEXT,                        -- путь к файлу или ссылка
    note TEXT,
    enabled INTEGER NOT NULL DEFAULT 1,
    order_index INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);
```

- [ ] Таблица + CRUD в `db/database.py`
- [ ] Экран или вкладка: список, редактирование, порядок, прайс-файл
- [ ] Экспорт и импорт справочника одним JSON — перенос на другую машину и
      откат после неудачной правки
- [ ] Тест: CRUD, экспорт → импорт → совпадение, импорт битого файла не рушит базу

### Приёмка

Направление заводится и редактируется без правки файлов; справочник выгружается
и загружается обратно; база v2 доезжает до текущей версии, бэкап лежит рядом.

## С2. Лид: модель, миграция, карточка

**Что меняется:** заявка перестаёт быть побочным продуктом бота и становится
карточкой, с которой работают — со статусом, историей и перепиской.

**Зависит от:** С1 (миграции, направления).

### Схема

```sql
-- расширение bot_leads до полной модели
tg_user_id, username, display_name, phone, email,
source_chat_id, source_type,        -- чат | ЛС | бот | ручной
direction_id, product, volume, unit, deadline, city, delivery,
status, score, owner,
next_action_at, next_action_text,
crm_id, crm_synced_at,
archived_at, reject_reason

CREATE TABLE lead_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    lead_id INTEGER NOT NULL,
    kind TEXT NOT NULL,          -- status | note | reminder | sync | created
    from_status TEXT,
    to_status TEXT,
    text TEXT,
    source TEXT NOT NULL,        -- ручной | сценарий | правило | интеграция
    created_at TEXT NOT NULL
);
```

Статусы: `новый → квалифицирован → отправлено КП → переговоры → сделка / отказ`.

- [x] Миграция: старые `bot_leads` доезжают без потери — `content` JSON
      разбирается по новым колонкам, что не разобралось остаётся в `content`
- [x] `status` старых заявок: `new → новый`, `in_progress → переговоры`,
      `closed → сделка`. Неоднозначность закрытых отмечается в `lead_events`
- [x] `core/lead.py` — домен: статусы, допустимые переходы, валидация.
      Первый модуль в `core`, без импортов Qt, Telethon, sqlite3
- [x] Тест на импорты: `core` не тянет `PySide6`, `telethon`, `aiogram`, `sqlite3`
- [x] Репозиторий лидов: создание, поиск, фильтры, смена статуса с записью события

### Карточка

- [x] Поля лида, редактируемые
- [x] История переходов из `lead_events`
- [x] Переписка с контактом — подтягивается из собранного через FTS
- [x] Заметки
- [x] Обязательная причина при переводе в «отказ», из списка
- [x] Файлы КП, приложенные к лиду

### Приёмка

Существующие заявки открываются как лиды после обновления; статус меняется и
попадает в историю; переписка видна в карточке; «отказ» без причины не сохраняется.

**Риск:** миграция `content` JSON — единственное место, где можно потерять данные
пользователя. Разбор консервативный: не уверены в поле — оставляем в `content`.

## С4. Outbox и защита аккаунта

**Что меняется:** ни одно сообщение не уходит мимо лимитов, а холодное первое
сообщение по умолчанию требует клика человека.

**Зависит от:** ничего — можно делать в любой момент, в том числе раньше С2.

**Почему дёшево:** отправка уже сходится в один callable
(`userbot_runner.make_send`). Это вставка слоя перед ним, а не переписывание
всех точек отправки.

- [x] `bots/outbox.py` — единственный путь наружу для сценариев, правил,
      напоминаний и ручных ответов (путь отличается от плана — не
      `services/telegram/outbox.py`, см. журнал)
- [x] Лимиты на аккаунт: сообщений в час, в сутки, отдельный лимит на первые
      сообщения новым контактам
- [x] Пауза между отправками с разбросом, тихие часы, выходные (пауза с
      разбросом уже была; тихие часы/выходные — новое, см. журнал)
- [x] FloodWait продлевает паузу, а не приводит к повтору (уже было в обоих
      раннерах до этой сессии, см. журнал)
- [x] Чёрный список и cooldown на контакт: не писать чаще раза в N дней
- [x] Режим dry-run: всё в журнал, наружу ничего
- [x] Черновики: холодное первое сообщение попадает в очередь черновиков,
      уходит по клику. Автоотправка — только ответом на входящее или после
      явного включения с показом предупреждения
- [x] Счётчики в интерфейсе: сколько отправлено за час и сутки, сколько осталось
- [x] Тест: при **любом** пути отправки лимиты применяются; dry-run не пропускает
      ни одного сообщения; черновик без клика не уходит

### Приёмка

Тест доказывает, что обойти outbox нельзя; счётчики видны; попытка холодной
рассылки показывает предупреждение и предлагает черновики.

## С5. Библиотека пресетов + мастер установки

**Что меняется:** рабочий сценарий ставится в два клика вместо часа настройки.

**Зависит от:** С1 (направления), С3 (создание лидов).

**Что не делаем:** графовую модель с семью типами узлов. Пресеты собираются на
существующем движке: развилки уже есть, `delay` заменяется триггером
`inactivity`, `condition` по времени — триггером `schedule`, `handoff` — действием
`notify_manager`. Экономия примерно четыре сессии при том же результате.

### Формат

JSON в `presets/`, версионируется, валидируется схемой при загрузке. Переменные
пресета (`manager_name`, `work_hours`, `directions`) спрашиваются мастером и
подставляются при установке.

- [ ] Схема пресета и валидация при загрузке
- [ ] Загрузчик: JSON → сценарий + шаблоны + триггеры + действия
- [ ] Мастер установки: имя менеджера, направления из справочника, рабочие часы,
      куда отдавать лид. Три-четыре вопроса, дальше сценарий редактируется как обычный
- [ ] Симулятор: расширить существующий «Прогнать сценарий» — показывать ветку,
      переменные и какие действия сработали бы
- [ ] Тест: каждый пресет прогоняется по всем веткам в симуляторе

### Пресеты

- [ ] `inbound_qualification` — разбор входящей заявки: направление → объём →
      срок → город → контакт → лид
- [ ] `price_request` — запрос прайса: отдаёт файл по направлению из справочника,
      фиксирует интерес, ставит задачу на КП
- [ ] `after_hours` — дежурный вне рабочих часов: обещает срок, собирает контакт,
      утром отдаёт менеджеру
- [ ] `chat_hunter` — ловля запросов в чатах: ключевые слова и стоп-слова из
      справочника → уведомление и **черновик** первого сообщения, без автоотправки
- [ ] `follow_up` — реанимация молчащих: касания на 3/7/14/30 день, останавливается
      при любом ответе (собирается на `inactivity`)

**Тон текстов:** B2B-поставки. Без восклицаний и продающего тона, короткие вопросы,
в каждом сценарии явная возможность сказать «свяжите с менеджером». Каждый пресет
работает сразу после установки, без правки текстов.

### Приёмка

Пресет ставится в два клика и сразу работает; тест проходит все ветки каждого
пресета; старые сценарии пользователя не затронуты.

## С6. Битрикс24: ядро и очередь

**Что меняется:** лид уходит в CRM сам, без ручного переноса.

**Зависит от:** С2.

- [ ] Входящий вебхук портала `https://<portal>/rest/<user_id>/<token>/`,
      учётные данные шифруются мастер-паролем
- [ ] `crm.duplicate.findbycomm` по телефону и email **перед** созданием
- [ ] `crm.lead.add`: TITLE, NAME, COMMENTS, SOURCE_ID, телефон, мессенджер TELEGRAM
- [ ] Обратная запись `crm_id` в лид; повторная отправка идёт через `crm.lead.update`
- [ ] Таблица очереди отправки, экспоненциальные ретраи, работа офлайн:
      без сети лиды копятся и уходят позже
- [ ] Кнопка «Проверить подключение» с понятным результатом
- [ ] Тест: дубль не создаётся повторно; отключённая сеть не теряет лидов и не
      роняет интерфейс; после восстановления очередь разбирается

### Приёмка

Интеграция настраивается без правки файлов; при выключенной сети лиды не теряются;
повторная отправка обновляет, а не плодит.

**Зависимость:** HTTP-клиент. `aiohttp` уже в зависимостях через `aiogram` —
новых библиотек не добавляем.

Чтобы не возвращаться к этим вопросам.

| Не делаем | Почему |
|---|---|
| Графовая модель сценария с 7 типами узлов | Ветвление работает и покрыто тестом. Роль `delay`/`condition`/`handoff` играют триггеры `inactivity`, `schedule` и действие `notify_manager` |
| Пресет `market_watch` | Это экран «Наблюдение», готов |
| Пресет `repeat_order` | Триггер `inactivity` + шаблон, настраивается за две минуты |
| Google Sheets | Экспорт в Excel есть, включая по расписанию. Fallback из плана — это то, что уже работает |
| Онбординг-мастер из 5 шагов | Пользователь один и он же заказчик, пройдёт однажды |
| Файл ресурсов строк | Ради второго языка, которого не будет. Механическая правка ~25 файлов впрок |
| Плагинный интерфейс интеграций | Впрок под amoCRM, которого нет в задаче |
| Скоринг лидов | Пять направлений и обозримый поток. Вернуться, когда лидов станет больше сотни |
| Перепланировка 14 экранов → 6 разделов | Экраны уже сгруппированы. «Лиды» добавляются третьим блоком в С3, остальное остаётся |
| Рефакторинг на 4 слоя отдельной задачей | Пользователю не даёт ничего. `core` растёт по касанию: `core/lead.py` в С2 |
| Разрыв `ui → data` отдельной задачей | 18 файлов интерфейса. Только по мере правок соседнего кода |
| Роли, синхронизация между копиями, сервер | Явно отложено в постановке |

### С1 — готова

**Миграции.** `db/migrations.py` — трекнутый список шагов вместо одной
идемпотентной функции. Старое поведение (весь `migrate()`, каким он был
до этой сессии) стало шагом «006» с флагом `self_healing=True` — он, как
и раньше, выполняется на каждом запуске независимо от того, что уже
отмечено применённым, потому что его собственные проверки внутри
(`_column_exists` и т.п.) сами по себе идемпотентны. Всё, что добавляется
после 006, — обычный одноразовый шаг: выполняется один раз, помечается в
`schema_migrations`, дальше не трогается — иначе откат немедленно
переприменялся бы на следующем запуске.

Решение по откату из плана подтверждено практикой: `down()` пишется только
там, где это один `DROP TABLE`/`ALTER`; общую защиту даёт обязательный
бэкап перед первым применением новой миграции к уже существующей базе
(`Database._backup_before_migration`, тот же `sqlite3 backup API`, что и у
`BackupService.backup_to`, — не сам `BackupService`, потому что на этом
шаге ещё нет мигрированной `Database`). На чистой установке бэкап не
создаётся — защищать нечего.

**Справочник направлений** — таблица `direction`, CRUD в `database.py`,
экран «Направления» в общих пунктах меню (общий для «Сбор» и «Боты»).
Список, порядок (↑/↓, перезапись `order_index`), редактирование через
диалог, экспорт/импорт в JSON (merge или полная замена, битые записи
пропускаются, а не роняют импорт).

**Найдено и исправлено по дороге, не входило в план:** таблицы с кнопками
в ячейках (`setCellWidget`) обрезали текст «Изменить»/«Удалить» до
нечитаемого вида на трёх экранах — новом «Направления», а также в уже
существующих «Наблюдение» и «Настройки → выгрузка по расписанию».
Причина: `resizeColumnsToContents()` меряет текст `QTableWidgetItem`, а не
`sizeHint()` виджета в ячейке, и без явной ширины колонка получалась уже
кнопки; `QPushButton` при этом не эллипсирует текст, а обрезает по центру
с обеих сторон, поэтому терялись именно первые буквы («Изменить» →
«зменить»). Поставлена явная ширина колонок с запасом над `sizeHint()`.
Отдельного отчёта не поднимал — правки однострочные, три файла, тот же
корень причины.

**Тесты:** `test_migration.py` расширен (учёт применённых миграций,
наличие `direction`), новые `test_migration_backup.py` (бэкап создаётся
один раз и только когда есть что защищать; откат снимает ровно
добавленное) и `test_directions.py` (CRUD, порядок, экспорт/импорт,
устойчивость к битым данным). 15 экранов открываются (было 14).

**Осталось на будущее, не блокирует С2:** `_backup_before_migration`
живёт в `Database`, а не в `BackupService`, сознательно — см. комментарий
в коде про цикличность. Если в С2+ понадобится показать бэкапы миграций
пользователю (не только в `data/backups/pre_migration/`), это отдельная
маленькая задача, не переделка.

### С2 — готова

**Домен.** `core/lead.py` — первый модуль в `core`, коды статусов остались
английскими/snake_case (как везде в схеме — `chats.status`, `bots.status`,
`bot_scenarios.kind`), русский только в словаре меток. «Допустимые
переходы» на практике оказались одним правилом: в «отказ» нельзя без
причины, всё остальное (пропуск стадий, возврат назад) не запрещено — у
одного человека без второго менеджера некому делать переходы, которые
стоило бы проверять. Цвета статус-пилюли (`STATUS_COLORS`) тоже переехали
сюда — это просто строки, не Qt-зависимость, а раньше дублировались бы
между списком лидов и карточкой.

**Миграция «008».** Расширяет `bot_leads` новыми колонками и добавляет
`lead_events`. Без `down()` — трогает не только схему, но и данные
(`status` старых заявок переписывается), поэтому это не однострочный шаг,
и защитой служит обязательный бэкап, а не откат. Ремап: `new → новый`,
`in_progress → переговоры` без вопросов; `closed → сделка` — с пометкой,
потому что старое «closed» означало и «продали», и «отказались», и это
единственное по-настоящему потерянное различие. Каждой перенесённой заявке
пишется событие `created`, бывшим «closed» — ещё и `status` с текстом
предупреждения. Идемпотентно: повторный прогон `migrate()` не плодит
вторые копии событий.

**Сознательно не перенёс из черновика плана в схему:** `score` (в плане
явно нет скоринга), `next_action_at`/`next_action_text` (это С3),
`crm_id`/`crm_synced_at` (С6/С7), `archived_at` (пока не нужен ни одной
сессии). Если понадобятся раньше срока — добавить колонку одной новой
миграцией, а не переделывать эту.

**Репозиторий и карточка.** `Database.add_lead` расширен новыми полями
(старые позиционные вызовы работают без изменений — заведён отдельный
тест на обратную совместимость), `set_lead_status` — единственный путь
смены статуса, всегда через `core.lead.validate_transition` и всегда с
записью в `lead_events`. `lead_card.py` — карточка с полями, историей,
вкладкой переписки (по `sender_id` через уже собранные сообщения) и
вложениями КП (просто список путей в JSON-колонке, без своего файлового
стора). Список лидов (`leads_tab.py`) — чипы фильтра теперь строятся из
`core.lead.ALL_STATUSES`, двойной клик и пункт меню открывают карточку.

**Найдено и исправлено по дороге, не входило в чек-лист сессии, но было
прямым следствием смены вокабуляра статусов:**
- `leads_tab.py._on_cell_clicked`/`_on_undo` (быстрая смена статуса по
  клику на пилюлю) писали статус напрямую через `set_lead_field`, в обход
  `set_lead_status` — новый статус применялся бы, но без записи в историю,
  то есть без выполнения собственного критерия приёмки этой же сессии.
  Исправлено до коммита, самостоятельно, до пользователя не доходило.
- `leads_tab.py._reassign` через `set_lead_field` жёстко ставил старый код

  переназначение менеджера больше не трогает статус вообще.
- `ui/screens/today.py` считал «в работе» по старому коду `in_progress` —
  после миграции такого значения в базе никогда не появится, счётчик тихо

- `bots/export.py` — Excel-выгрузка лидов держала свой собственный
  `_STATUS_LABELS` с тремя старыми кодами; новые статусы выгружались бы

- `Database.leads_funnel()` (сводка на экране «Аналитика») группировала по
  старым трём кодам — «в работе» и «закрыты» стали бы вечными нулями.

**Тесты:** `test_core_no_qt.py` (AST-проверка на отсутствие Qt/Telethon/

### С3 — готова

**Миграция «009».** Два независимых изменения в одном шаге: колонки
`next_action_at`/`next_action_text`, и снятие `NOT NULL` с `bot_leads.
contact_id`/`bot_id` — до этой сессии каждый лид обязан был прийти от
бота, а «завести откуда угодно» означает, что теперь бывает и лид без
бота, и лид без привязанного контакта. SQLite не умеет снимать
ограничение колонки на месте, поэтому таблица перестраивается тем же
способом, что уже был в `_migrate_scenario_sessions_unique` (копия →
drop → rename → переиндексация) — не новая идея, а второй случай того
же приёма. Собственных полей лида (display_name/phone/tg_user_id и
так далее, С2) достаточно, чтобы карточка и списки показывали лид без
`contact_id` не хуже, чем с ним.

**Наступил на то же грабли, что предупреждал в комментарии.** Список
колонок перестройки фиксирован на момент миграции; я сначала дописал
`ALTER TABLE ADD COLUMN next_action_at/next_action_text`, а потом
вызвал перестройку — которая тут же выбросила обе только что
добавленные колонки, потому что копирует по своему жёсткому списку.
Нашёл сразу же, тестом (`next_action_at` не находилась при первой же
попытке `set_lead_field` в `test_lead_lifecycle.py`), поменял порядок:
сначала перестройка, потом добавление новых колонок — как и было
написано в докстринге функции, просто не в том порядке, в котором я
сам её вызвал.

**Заведение «откуда угодно» — три пути, все через `add_lead` с
`contact_id=None, bot_id=None`:**
- Вручную: кнопка «＋ Новая заявка» на экране лидов → `NewLeadDialog`
  (новый файл `lead_create_dialog.py`) → сразу открывается обычная
  карточка для остального.
- Из найденного сообщения: кнопка «Создать лид» на карточке сообщения
  в «Собранном», и пункт контекстного меню на строке в «Наблюдении».
  Оба берут identity прямо из строки сообщения (tg_user_id/username/
  display_name/chat_id) — без создания `bot_contacts`-записи: у лида
  уже есть свои поля для этого с С2, плодить контакт не от бота незачем.
- Из сценария: другое решение, чем в черновике плана — не отдельное
  действие `create_lead` в редакторе правил, а сопоставление на уровне
  шага сценария. У каждого шага теперь есть необязательное поле
  «→ поле лида» (`scenario_screen.py`, `step["lead_field"]`, восемь
  значений — `core.lead.SCENARIO_LEAD_FIELDS`, без направления: тому
  нужен id из справочника, а не текст ответа). `content` по-прежнему
  получает сырые ответы целиком — сопоставление только дополняет, не
  заменяет, несопоставленное поле не пропадает. Расхождение с
  формулировкой плана раскрыто явно; причина — сама генерация лида по
  завершении сценария и так уже не была отдельным «действием» в
  редакторе правил (это встроенное поведение `run_scenario`/
  `continue_scenario`), а плодить настоящее отдельное действие ради
  того же самого результата не стоило лишнего слоя.

**Напоминания.** `LeadReminderService` — тот же тик-цикл на asyncio, что
у `ExportScheduleService`, раз в 60 секунд, «прошло время — а не сейчас
ли ровно тот час» (переживает уснувшую машину). Дедупликация — не
отдельный флаг, а сам факт очистки `next_action_at`/`next_action_text`
при срабатывании: `due_lead_reminders()` смотрит только на это поле,
так что повторный тик (и тем более новое соединение с базой после
рестарта) просто не находит уже сработавшее напоминание. Запись в
`lead_events` (`kind=reminder`, ранее объявлен в С2, но не использовался)
остаётся постоянным следом даже после очистки поля. Показ — тот же
`TrayController.notify`, что у совпадений в «Наблюдении».

**Список и воронка.** `list_leads()` — новые необязательные фильтры
`direction_id`/`source_type`/`since`/`until`, обратная совместимость
не пострадала (позиционные `bot_id`/`status` не тронуты). Воронку не
стал делать отдельным виджетом: чипы фильтра статуса и так кликом
проваливаются в список, им просто дописан счётчик (`leads_status_
counts()`, одним `GROUP BY`) — то же требование («сколько на каждом
статусе, клик проваливается в список»), без дублирующего бруска рядом.

**Блок «Лиды» в навигации.** `main_window.py`: `BLOCKS` — третий пункт,
`NAV_BY_BLOCK["leads"]` — экран `leads` переехал туда из `bots`.
Бейдж нового счётчика лидов тоже переехал: раньше он показывался на
кнопке блока «Боты» (`bots_block`, вместе с «!» от упавших ботов),
теперь у «Лиды» свой бейдж, а «Боты» показывает только «!».

**Найдено и исправлено по дороге, не входило в чек-лист, но было прямым
следствием «лид без бота»:**
- `bots/export.py` — Excel-выгрузка брала имя контакта и telegram id
  только из join на `bot_contacts`/`bots`; для лида без `contact_id`/
  `bot_id` это были бы пустая колонка и «бот None». Переведено на

### С4 — готова

**Что уже было, а что действительно новое.** Прежде чем строить, проверил
по факту: пауза с разбросом между отправками, кулдаун на контакт и
FloodWait (продление паузы, а не повтор с нуля) уже существовали в
`userbot_runner.make_send` и были покрыты `test_send_limits.py`. Но
**только там** — у `BotApiRunner.send_dm` (aiogram, Bot API) не было вообще
никакой защиты: ни паузы, ни кулдауна, ни лимитов, только тот же
FloodWait-ретрай. Двух раздельных путей отправки без общего слоя — и
есть та причина, по которой это сессия С4, а не мелкая правка.

**`bots/outbox.py`, не `services/telegram/outbox.py`.** Отклонение от
черновика плана: outbox должен оборачивать `make_send`/`BotApiRunner.
send_dm` и читать `bots.settings` — оба уже живут в `bots/`, и
`services/` в этом приложении ни разу не тянется в `bots/` (только
наоборот). Заводить новый вложенный пакет `services/telegram/` только
ради буквального пути значило бы придумывать структуру, которой больше
нигде в проекте нет.

**`reactive` — единственное, что нельзя вывести из пары (target, text).**
Обёртка `Outbox.wrap(bot_id, raw_send, reactive=...)` решает, что
происходит с сообщением, но «это ответ на входящее или сообщение по
инициативе бота» ниоткуда не следует из самих аргументов — это должен
сказать вызывающий код. Реактивно: `RulesEngine.fire`/`continue_scenario`,
вызванные из `_handle_new_message`/`_handle_message` обоих раннеров
(контакт только что написал) и повторная отправка черновика по клику
(`BotManager.send_draft` — человек только что решил). Проактивно: то же
самое, но вызванное из `TriggerScheduler` (`schedule`/`inactivity` —
никто ничего не писал). Тихие часы и персистентный (в днях, не в
секундах) кулдаун на контакт действуют только на проактивные — отвечать
человеку, который только что написал, в три часа ночи не грех, а вот
самим писать в три ночи — грех. Лимит в час/сутки и лимит первых
сообщений в сутки действуют на оба пути: всплеск ответов на входящие
тоже может выглядеть как спам.

**Холодное первое сообщение → черновик, не отправка.** Если это
проактивная отправка и `outbox_sends` не хранит ни одной строки
`status='sent'` для этой пары (бот, адресат) — это первое сообщение,
и при выключенном `auto_send_cold` (по умолчанию) оно уходит в
`outbox_drafts`, `raw_send` не вызывается вообще. Экран «Боты» получил
панель «Черновики» — единственное место, откуда они уходят, по кнопке.
Включение `auto_send_cold` в `SendLimitsDialog` спрашивает подтверждение
через `QMessageBox` — ровно предупреждение, которого просит инвариант 6.

**Дедупликация лимитов — своя таблица, не `bot_activity_log`.**
`bot_activity_log` пишет только входящие события (`trigger_fired`) и
пару специальных меток планировщика — ни одной реальной попытки
отправки там никогда не логировалось. `outbox_sends` — новая таблица
именно для этого: каждая попытка (sent/blocked/dry_run), с флагом
`is_first`, откуда считаются часовой/суточный лимиты, лимит первых
сообщений и «когда мы в последний раз писали этому контакту» —
персистентно, без in-memory состояния, переживает рестарт (проверено
тестом на новом соединении с базой, тот же приём, что у С3-напоминаний).

**Что сознательно упрощено:** чёрный список и все лимиты — на бота, не
на Telegram-аккаунт целиком (несколько ботов на одном аккаунте не
складывают лимиты друг с другом). Решение по аналогии с уже
существующим `bots.settings` — тоже на бота, не на аккаунт; полноценная
привязка к `account_id` не по плану буквально и не стоила лишнего слоя
в рамках одной сессии.

**Не сделано из-за журнала «что уже есть»:** карта сессий отмечала
`ui/screens/settings.py` (1036 строк) на разрезание «в С4 и С6» — этот
файл в этой сессии не тронут вообще, новый интерфейс (лимиты, тихие
часы, чёрный список, черновики) целиком лёг в уже существующий диалог
на боте (`SendLimitsDialog`) и новую панель под списком ботов, а не в
`settings.py`. Разрезание `settings.py` остаётся на С6 или отдельной
мелкой задачей — не забыто, просто не понадобилось для этой сессии.

**Найдено по дороге:** `Outbox.wrap` изначально использовал
`dt.datetime.now()` (наивное время) и сравнивал его с `outbox_sends.
created_at` (со смещением, тот же формат, что и `now_iso()`) —
`TypeError` при вычитании. Поймано первым же тестом на персистентный
кулдаун, исправлено на `.astimezone()`, как везде в проекте.
`db.outbox_counts()` в первой версии сам считал лимиты через
`bots.settings` — убрано: `db/` не должен импортировать `bots/`, это
разворот обычного направления зависимостей приложения. Метод теперь
отдаёт только сырые счётчики, лимиты подставляет `SendLimitsDialog`,
который и так уже читает `bot_settings`.

**Тесты:** `test_outbox.py` (новый) — dry-run не пропускает ничего,
реактивная первая отправка уходит сразу, проактивная холодная — в
