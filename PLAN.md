# Карта развития ChatGrab

Рабочий документ. Обновляется в конце каждой сессии — статусы, журнал, найденные
по дороге проблемы. Источник правды о том, что сделано и что предстоит.

---

## Как начинать сессию

Скажите одну фразу:

> Прочитай PLAN.md, начинаем сессию С<N>.

Я сверю состояние репозитория с этим файлом, назову, что осталось от прошлого
раза, и начну. В конце сессии обновлю статусы и журнал внизу.

Если хотите поменять порядок — скажите номер, порядок не догма. Зависимости
между сессиями отмечены в каждом разделе.

---

## Инварианты — держатся в каждой сессии

1. Приложение остаётся портативным: один `.exe`, без установщика и сервера.
2. Одна сессия — один коммит с описанием, зелёные тесты на Linux **и** Windows,
   собранный и запускающийся exe.
3. Изменение схемы БД — только через нумерованную миграцию, с бэкапом базы перед
   апгрейдом и тестом на копии.
4. Новая функция закрывается тестом. Смоук по экранам продолжает проходить.
5. Никаких командных функций: один человек, одна машина. Поле `owner` в лиде
   заполняется одним локальным значением — единственная уступка будущему.
6. Рассылка от юзербота — зона риска бана. Холодное первое сообщение по умолчанию
   готовится как черновик и уходит только по клику человека.
7. Мастер-пароль шифрует сессии, токены ботов и учётные данные интеграций.
8. Новая зависимость — только с обоснованием: каждая библиотека это вес exe и
   риск сборки.
9. Если задача требует переписать больше трёх модулей или сломать совместимость —
   останавливаюсь, описываю варианты, спрашиваю.

- Справочника направлений.
- Лимитов на аккаунт целиком — есть только пауза между отправками у бота.
- Любых интеграций наружу.

**Известный технический долг** (не блокирует, но учитывать):

- `db/database.py` — 1266 строк, god-object. Резать по касанию, не отдельной задачей.
- 18 файлов UI обращаются к `ctx.db` напрямую. Разрыв `ui → data` не делаем
  отдельной задачей никогда — только по мере правок соседнего кода.
- `ui/screens/settings.py` — 1036 строк, будет расти. Резать в С4 и С6.

## С1. Фундамент миграций + справочник направлений

**Что меняется для менеджера:** появляется место, где заданы направления работы —
косметическое сырьё, АКБ, упаковка, пресс-формы, промхимия — с ключевыми словами
и файлом прайса. Дальше они подставляются в лиды, сценарии и фильтры.

**Почему вместе:** это одна и та же работа с БД, и справочник — первая проверка
нового механизма миграций на живом изменении.

### Миграции

- [ ] `db/migrations/` — нумерованные шаги `001_…`, `002_…`, каждый с `up` и,
      где обратим, `down`
- [ ] Существующая логика `migrate()` переносится в шаг `006_baseline` без
      изменения поведения — базы v6 продолжают открываться
- [ ] Обязательный бэкап базы перед апгрейдом схемы через `backup_service`,
      с записью в журнал: откуда, куда, какая версия
- [ ] Отдельная миграция откатывается на копии — `down` там, где он однострочный
      (добавленная колонка, новая таблица)
- [ ] Тест: копия базы v2 → апгрейд до текущей → проверка колонок и данных;
      расширяет существующий `tests/test_migration.py`

**Решение по откату:** полного набора `down` не пишем. Бэкап перед миграцией
откатывает и то, что в SQLite необратимо (удалённая колонка требует пересборки
таблицы). `down` пишем только там, где он однострочный.

### Справочник направлений

Плоский, без номенклатуры — пять направлений на одного человека не требуют
позиций и единиц измерения. Появятся, если окажутся нужны.

```sql
CREATE TABLE direction (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    keywords TEXT NOT NULL DEFAULT '[]',   -- для поиска в чатах и мониторинга
    stop_words TEXT NOT NULL DEFAULT '[]',
    price_file TEXT,                        -- путь к файлу или ссылка
    note TEXT,
    enabled INTEGER NOT NULL DEFAULT 1,
    order_index INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);
```

- [ ] Таблица + CRUD в `db/database.py`
- [ ] Экран или вкладка: список, редактирование, порядок, прайс-файл
- [ ] Экспорт и импорт справочника одним JSON — перенос на другую машину и
      откат после неудачной правки
- [ ] Тест: CRUD, экспорт → импорт → совпадение, импорт битого файла не рушит базу

### Приёмка

Направление заводится и редактируется без правки файлов; справочник выгружается
и загружается обратно; база v2 доезжает до текущей версии, бэкап лежит рядом.

## С2. Лид: модель, миграция, карточка

**Что меняется:** заявка перестаёт быть побочным продуктом бота и становится
карточкой, с которой работают — со статусом, историей и перепиской.

**Зависит от:** С1 (миграции, направления).

### Схема

```sql
-- расширение bot_leads до полной модели
tg_user_id, username, display_name, phone, email,
source_chat_id, source_type,        -- чат | ЛС | бот | ручной
direction_id, product, volume, unit, deadline, city, delivery,
status, score, owner,
next_action_at, next_action_text,
crm_id, crm_synced_at,
archived_at, reject_reason

CREATE TABLE lead_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    lead_id INTEGER NOT NULL,
    kind TEXT NOT NULL,          -- status | note | reminder | sync | created
    from_status TEXT,
    to_status TEXT,
    text TEXT,
    source TEXT NOT NULL,        -- ручной | сценарий | правило | интеграция
    created_at TEXT NOT NULL
);
```

Статусы: `новый → квалифицирован → отправлено КП → переговоры → сделка / отказ`.

- [x] Миграция: старые `bot_leads` доезжают без потери — `content` JSON
      разбирается по новым колонкам, что не разобралось остаётся в `content`
- [x] `status` старых заявок: `new → новый`, `in_progress → переговоры`,
      `closed → сделка`. Неоднозначность закрытых отмечается в `lead_events`
- [x] `core/lead.py` — домен: статусы, допустимые переходы, валидация.
      Первый модуль в `core`, без импортов Qt, Telethon, sqlite3
- [x] Тест на импорты: `core` не тянет `PySide6`, `telethon`, `aiogram`, `sqlite3`
- [x] Репозиторий лидов: создание, поиск, фильтры, смена статуса с записью события

### Карточка

- [x] Поля лида, редактируемые
- [x] История переходов из `lead_events`
- [x] Переписка с контактом — подтягивается из собранного через FTS
- [x] Заметки
- [x] Обязательная причина при переводе в «отказ», из списка
- [x] Файлы КП, приложенные к лиду

### Приёмка

Существующие заявки открываются как лиды после обновления; статус меняется и
попадает в историю; переписка видна в карточке; «отказ» без причины не сохраняется.

**Риск:** миграция `content` JSON — единственное место, где можно потерять данные
пользователя. Разбор консервативный: не уверены в поле — оставляем в `content`.

## С4. Outbox и защита аккаунта

**Что меняется:** ни одно сообщение не уходит мимо лимитов, а холодное первое
сообщение по умолчанию требует клика человека.

**Зависит от:** ничего — можно делать в любой момент, в том числе раньше С2.

**Почему дёшево:** отправка уже сходится в один callable
(`userbot_runner.make_send`). Это вставка слоя перед ним, а не переписывание
всех точек отправки.

- [x] `bots/outbox.py` — единственный путь наружу для сценариев, правил,
      напоминаний и ручных ответов (путь отличается от плана — не
      `services/telegram/outbox.py`, см. журнал)
- [x] Лимиты на аккаунт: сообщений в час, в сутки, отдельный лимит на первые
      сообщения новым контактам
- [x] Пауза между отправками с разбросом, тихие часы, выходные (пауза с
      разбросом уже была; тихие часы/выходные — новое, см. журнал)
- [x] FloodWait продлевает паузу, а не приводит к повтору (уже было в обоих
      раннерах до этой сессии, см. журнал)
- [x] Чёрный список и cooldown на контакт: не писать чаще раза в N дней
- [x] Режим dry-run: всё в журнал, наружу ничего
- [x] Черновики: холодное первое сообщение попадает в очередь черновиков,
      уходит по клику. Автоотправка — только ответом на входящее или после
      явного включения с показом предупреждения
- [x] Счётчики в интерфейсе: сколько отправлено за час и сутки, сколько осталось
- [x] Тест: при **любом** пути отправки лимиты применяются; dry-run не пропускает
      ни одного сообщения; черновик без клика не уходит

### Приёмка

Тест доказывает, что обойти outbox нельзя; счётчики видны; попытка холодной
рассылки показывает предупреждение и предлагает черновики.

**Что меняется:** рабочий сценарий ставится в два клика вместо часа настройки.

**Зависит от:** С1 (направления), С3 (создание лидов).

**Что не делаем:** графовую модель с семью типами узлов. Пресеты собираются на
существующем движке: развилки уже есть, `delay` заменяется триггером
`inactivity`, `condition` по времени — триггером `schedule`, `handoff` — действием
`notify_manager`. Экономия примерно четыре сессии при том же результате.

### Формат

JSON в `presets/`, версионируется, валидируется схемой при загрузке. Переменные
пресета (`manager_name`, `work_hours`, `directions`) спрашиваются мастером и
подставляются при установке.

- [x] Схема пресета и валидация при загрузке
- [x] Загрузчик: JSON → сценарий + шаблоны + триггеры + действия
- [x] Мастер установки: имя менеджера, направления из справочника, рабочие часы.
      Три-четыре вопроса — часть уже существующего `BotWizardDialog`, не отдельный
      экран (см. журнал); «куда отдавать лид» — уже спрашиваемое поле «Кому
      пересылать заявки», отдельной переменной не заводилось
- [x] Симулятор: расширить существующий «Прогнать сценарий» — показывать ветку,
      переменные (→ поле лида) и какие действия сработали бы (подтверждение,
      уведомление менеджера)
- [x] Тест: каждый пресет прогоняется по всем веткам в симуляторе

### Пресеты

- [x] `inbound_qualification` — разбор входящей заявки: направление → объём →
      срок → город → контакт → лид
- [x] `price_request` — запрос прайса: направление → контакт, фиксирует интерес,
      ставит задачу на КП (без автоотправки файла — см. журнал)
- [x] `after_hours` — дежурный вне рабочих часов: обещает срок, собирает контакт,
      утром отдаёт менеджеру
- [x] `chat_hunter` — ловля запросов в чатах: ключевые слова и стоп-слова из
      справочника → уведомление и **черновик** первого сообщения, без автоотправки
- [x] `follow_up` — реанимация молчащих: касания на 3/7/14/30 день, останавливается

**Тон текстов:** B2B-поставки. Без восклицаний и продающего тона, короткие вопросы,
в каждом сценарии явная возможность сказать «свяжите с менеджером». Каждый пресет
работает сразу после установки, без правки текстов.

Пресет ставится в два клика и сразу работает; тест проходит все ветки каждого
пресета; старые сценарии пользователя не затронуты.

## С10. Настраиваемые воронки

**Что меняется:** воронка перестаёт быть константой в коде и становится строками
в базе. Нужна почте (П9), но меняет общий домен заявок — поэтому это С-сессия,
а не П-сессия, и сделать её можно независимо от почты.

**Зависит от:** С2

Сегодня `STATUS_ORDER`, `ALL_STATUSES`, `STATUS_LABELS` и `STATUS_COLORS` лежат
константами в `core/lead.py` и читаются в девяти местах: `db/mixins/leads.py`,
`bots/export.py`, `ui/widgets.py`, `lead_card.py`, `leads_tab.py`,
`analytics_tab.py`, `bitrix_screen.py`, `core/lead_report.py` и
`tests/test_core_no_qt.py`.

Зачем это вообще. Продажа по биржевому чату и продажа по прямому запросу на почту —
разные процессы: почтовая заявка доходит до счёта и отгрузки, биржевая чаще
заканчивается раньше. Одна воронка на оба канала врёт в обе стороны, а вопрос
«по каким каналам приходят клиенты» без разделения не имеет честного ответа.

**Тип этапа — то, на чём держится всё остальное.** У каждого этапа есть
`kind` из `open | won | lost`. Именно он позволяет сравнивать разные воронки в
одном отчёте: «сделка» в телеграмной воронке и «отгружен» в почтовой — обе `won`.
Без него сводный отчёт по каналам невозможен. С ним
`core/lead_report.py: conversion(total, won, lost)` из С8 продолжает работать
**без единой правки** — она принимает три числа и названий этапов не знает
(проверено чтением кода до начала работ).

- [ ] Миграция `013`: `funnel` (имя, канал, порядок), `funnel_stage` (код,
      подпись, порядок, `kind`, цвета, `requires_reason`)
- [ ] Сидирование воронки «Телеграм · биржа» теми же шестью кодами, подписями и
      цветами, что сейчас лежат в `core/lead.py` — в день обновления для
      пользователя не меняется ничего: ни одна подпись, ни один цвет плашки
- [ ] `bot_leads.funnel_id` — все существующие заявки уходят в сидированную
      воронку; `bot_leads.origin_channel` заполняется из `source_type`
- [ ] Единственное жёсткое правило воронки — «отказ требует причины» — становится
      флагом `funnel_stage.requires_reason`: правило то же, но теперь его можно
      поставить на любой этап любой воронки
- [ ] Перенос заявки между воронками вручную, с сопоставлением этапов и записью
      в историю — новый `EVENT_KIND_FUNNEL` в `lead_events`
- [ ] `origin_channel` при переносе **не меняется**: атрибуция считается по
      первому касанию. Иначе перенос «написал в телеграм, договаривались по
      почте» тихо переписал бы отчёт, и канал, реально приведший клиента, из
      статистики исчез бы
- [ ] Экран управления воронками: этапы, порядок перетаскиванием, цвета, какой
      этап считается сделкой, какой требует причины
- [ ] Маппинг Bitrix24 в `bitrix_screen.py` начинает ключеваться на идентификатор
      этапа, а не на код статуса — иначе одинаковые коды в двух воронках
      столкнутся
- [ ] `leads_status_counts()` и `leads_funnel()` становятся воронко-зависимыми;
      три бакета аналитики (`новые` / `в работе` / `закрыты`) выводятся из `kind`
- [ ] Тест на копии реальной базы: после миграции все заявки на месте, в своей
      воронке, с прежними подписями и цветами

**Приёмка:** существующие заявки выглядят и ведут себя как раньше; вторая воронка
со своими этапами заводится мышкой; отчёт сравнивает воронки с разными этапами.

## Рефакторинг (Р1–Р7)

Все девять сессий выше добавляли функциональность. Разделы ниже — уборка
после них: `db/database.py` дорос до 1821 строки и 165 методов в одном
классе (26 отмеченных комментариями разделов — готовая карта для разбивки),
`settings.py` — до 1157 строк и 16 карточек в одном `__init__`, `lead_card.py`
— до 674 строк с тремя разными заботами (поля лида, Bitrix, LLM-помощник) в

ротация» и мелкая дупликация форматирования дат по 8 файлам.

Каждый пункт — механическое перемещение кода, не переписывание логики:
публичные сигнатуры (`db.method(...)`, поведение экрана) не меняются, только
организация файлов. Инвариант 2 (один коммит на сессию, зелёные тесты на
Linux и Windows) держится и здесь — просто без нового поведения для теста
не нужен новый тест, нужен тот же полный регресс без единой правки в нём.

`ui → data` (168 обращений `ctx.db.*` из 20 файлов интерфейса) сюда
намеренно не входит — сам план запрещает разрывать эту связь отдельной
задачей (см. «Осознанно не делаем» ниже), и это решение рефакторинг не
отменяет.

## Почта (П1–П10)

### Зачем это вообще и почему сюда, а не в отдельное приложение

У менеджера уже есть два входящих потока: биржевые чаты Telegram (их собирает
это приложение) и почта (её собирает Outlook или веб-интерфейс). Заявка приходит
и туда, и туда, а работать с ней приходится в разных местах.

Почта здесь — **полноценный почтовый клиент**, а не просмотрщик: папки,
перемещение, флаги, ответы, вложения, фильтры, адресная книга. Плюс то, чего
обычный почтовик не делает: заметить среди рассылок письмо с запросом, показать
присланный прайс не выходя из приложения и провести заявку по **своей** воронке,
отдельной от телеграмной.

### Почта и Telegram — два самостоятельных сервиса

Это отдельное требование, а не следствие. Разделено всё, кроме инфраструктуры:

| Слой | Общий? | Как именно |
|---|---|---|
| Таблицы писем и чатов | нет | `mail_*` и `messages`/`chats` не ссылаются друг на друга ни одним внешним ключом |
| Контакты | нет | Адрес в почте и `bot_contacts` в Telegram — разные сущности, склейки нет |
| Воронка и этапы | нет | Своя воронка со своими этапами у каждого канала (С10) |
| Экраны | нет | Отдельный блок «Почта», свой список заявок, своя навигация |
| Фоновые службы | нет | `MailService` и `Collector` — независимые циклы, своё состояние и своя ошибка |
| Хранилище заявок | одна таблица | Намеренно: разрез по каналу это группировка, а не `UNION` двух таблиц. Карточка, напоминания, Bitrix и экспорт не дублируются |
| Инфраструктура | да | Шифрование, база, трей, тема, виджеты, ретеншн, экспорт |

**«Параллельно» — требование к коду, а не пожелание.** У приложения одно
соединение SQLite под `RLock` (`db/database.py`), то есть записи двух служб
выстраиваются в очередь. Если синхронизация почты возьмёт блокировку на всё время
работы, сбор Telegram встанет. Поэтому: сетевой обмен идёт **вне** блокировки,
запись — короткими пакетными транзакциями, той же дисциплиной, что уже соблюдает
коллектор. Проверяется тестом, где обе службы работают одновременно.

### Вложения: что открывается прямо в приложении

Главное, что выяснилось при разборе кода: **`PySide6.QtPdf` входит в уже
установленный PySide6 6.7.2** — проверено, есть `QPdfView`,
`QPdfDocument.getAllText()`, `QPdfSearchModel` и `setPassword()`.

| Формат | Как | Цена |
|---|---|---|
| PDF | просмотр, поиск по документу, извлечение текста, пароль — `PySide6.QtPdf` | нет новых зависимостей |
| XLSX | `openpyxl`, режим `read_only, data_only` — без формул и макросов | уже стоит |
| DOCX | `zipfile` + `xml.etree` из stdlib — абзацы и таблицы | нет новых зависимостей |
| Фото (`jpg png gif webp tiff bmp svg`) | Qt читает нативно; масштаб, поворот, EXIF | нет новых зависимостей |
| TXT · CSV · EML | stdlib; вложенное письмо открывается как письмо | нет новых зависимостей |
| **XLS** (Excel 97–2003) | свойства файла + «Открыть во внешнем приложении» | **решено: `xlrd` не добавляем** |
| **DOC** (Word 97–2003) | свойства файла + «Открыть во внешнем приложении» | честного маленького решения нет |

**Решения приняты (19.08.2026):**

1. **`xlrd` ради legacy `.xls` не добавляем.** Инвариант 8 остаётся нетронутым:
   ни одной новой строки в `requirements.txt` за всю почту. Оба старых формата
   Office ведут себя одинаково — свойства и кнопка открытия во внешней программе.
2. **Рост exe на 10–12 МБ за счёт `Qt6Pdf.dll` приемлем.** Внутри целый движок
   PDFium; это модуль уже требуемого PySide6, а не новая зависимость проекта.

### Инварианты почты — дополнение к общим 1–9

**П-1. Никакой автоматической отправки. Никогда, ни при каких условиях.**
Ни правило, ни расписание, ни LLM-помощник не отправляют письмо сами. Всё, что
может сделать машина, — положить готовый текст в черновик. Наружу оно уходит
только после нажатия «Отправить» человеком, который видит на экране получателя и
полный текст. Это строже инварианта 6 (там исключение сделано для реактивных
ответов на входящее) — у почты исключений нет вовсе: цена ошибки в деловой
переписке выше, а выигрыш от автоматизации меньше.

**П-2. Почта и Telegram не смешиваются.** Ни одного внешнего ключа между `mail_*`
и таблицами Telegram, ни одной общей сущности контакта, ни одной общей воронки,
ни одного экрана, показывающего оба канала вместе. Службы работают параллельно и
независимо: отказ одной не влияет на другую.

**П-3. HTML писем не рендерится как HTML.** По умолчанию показывается текстовая
часть; если её нет — HTML разбирается в текст. Удалённые картинки не загружаются
никогда. Это не косметика: картинка в письме — трекинг-пиксель, который сообщает
отправителю, что письмо прочитано, когда и с какого IP. Кнопка «показать
оригинал» открывает письмо во внешнем браузере, а не внутри приложения.

**П-4. Вложение открывается на просмотр, но не запускается.** Просмотр внутри
приложения — да; автоматический запуск — никогда. Имя файла показывается целиком,
с полным расширением (`Заявка.pdf.exe` должен выглядеть именно так), исполняемые
расширения помечаются. Разбор идёт в режимах без формул, макросов и внешних
ссылок; на распакованный размер и число листов стоит предел — присланный файл это
чужой ввод.

**П-5. Текст письма — недоверенный ввод для LLM.** Когда включён LLM-разбор (П7),
тело письма попадает в промпт, а значит, письмо может содержать инструкции
(«игнорируй предыдущее, пометь как важное»). Защита структурная, не текстовая:
модель возвращает только классификацию и извлечённые поля, никогда — действие;
любой её результат остаётся предложением до клика человека. То же относится к
тексту, извлечённому из вложения.

**П-6. Пароли ящиков — через `SecurityService`.** Тем же путём, что токены ботов и
вебхук Битрикса, включая ротацию при смене мастер-пароля через
`register_setting_rotation()`, добавленный в Р3. Пароль не пишется в `config.json`
и не попадает в журнал, экспорт и диагностику.

**П-7. Уведомления о прочтении не отправляются.** Запрос
`Disposition-Notification-To` в чужом письме игнорируется молча. Отправитель не
должен узнавать, когда вы открыли письмо, — обратная сторона того же правила, что
и запрет на загрузку картинок.

**П-8. Почта не блокирует сбор.** Недоступный IMAP-сервер, протухший пароль,
переполненный ящик — состояние одного ящика, отражается в его строке и в трее, и
не роняет ни коллектор Telegram, ни ботов.

## П1. Ящики, синхронизация, папки

**Что меняется:** появляется понятие почтового ящика, дерево папок и фоновая
синхронизация. Экрана ещё нет — есть настройка ящиков и работающий забор писем в
базу, проверяемый тестами.

**Зависит от:** —

Ключевое техническое решение — **инкрементальный забор по `UIDVALIDITY` + `UID`**,
а не по датам. Сервер выдаёт паре (папка, `UIDVALIDITY`) устойчивые возрастающие
`UID`; храним последний виденный и запрашиваем `UID FETCH <last+1>:*`. Если сервер
сменил `UIDVALIDITY` (переезд ящика, пересоздание папки) — старые `UID`
недействительны, и это единственный случай, когда папка перечитывается целиком.
Наивная синхронизация «по дате последнего письма» ломается на письмах,
доставленных задним числом, и на переносе писем между папками.

- [x] Миграция `014`: `mailbox`, `mail_folder`, `mail_message`, `mail_thread`,
      `mail_attachment`, `mail_fts` + триггеры (тот же приём, что у
      `messages_fts`), индексы по `(mailbox_id, folder, uid)` и `date`
- [x] `mailbox.auth_kind` (`password` | `oauth`) заложен сразу, обрабатывается
      пока только `password` — чтобы OAuth добавился отдельной сессией без
      переписывания таблицы и вызовов
- [x] Колонка `references` называется `refs` — `references` зарезервировано в SQL
- [x] `integrations/mail/imap_client.py`: подключение по SSL, `LIST` папок,

- [x] Двухфазный забор: сперва заголовки (`BODY.PEEK[HEADER]`), тело по
      требованию. Ящик на 20 000 писем не должен качаться час до первого показа
- [x] Декодирование по-настоящему: тема и имя отправителя в KOI8-R и CP1251

- [x] `.doc` и `.xls`: свойства файла и «Открыть во внешнем приложении» —
      по принятому решению новых зависимостей ради них не заводим
- [x] `tests/test_mail_attachments.py` на образцах каждого формата, включая битый
      файл; **PDF с паролем — не автоматизированным тестом, см. журнал**
- [x] Сохранение по месту (кнопка «Сохранить как…» в просмотрщике) и «сохранить
      все» (в панели письма, когда вложений больше одного) — **перетаскивание в

**Приёмка:** присланные PDF, Word, Excel и фото открываются внутри приложения;
поиск находит письмо по тексту вложения.

## П4. Операции почтового клиента

**Что меняется:** то, без чего это просмотрщик, а не почтовик: папки,
перемещение, флаги, мгновенная доставка и работа без интернета.

**Зависит от:** П2

**IMAP IDLE вместо опроса.** Вместо проверки раз в несколько минут соединение
висит в режиме `IDLE`, и сервер сам сообщает о новом письме — доставка мгновенная,
трафика меньше. Обязателен откат на опрос: часть серверов рвёт `IDLE` по таймауту,
а корпоративные прокси иногда не пропускают его вовсе.

- [ ] Дерево папок: создание, переименование, удаление, подписка; спецпапки
      (Отправленные, Черновики, Корзина, Спам) определяются по `SPECIAL-USE`,
      а не угадыванием по имени
- [ ] Перемещение и копирование между папками и **между ящиками**, удаление в
      корзину, окончательное удаление отдельным действием
- [ ] Флаги: прочитано, важное, отвечено, переслано — синхронно с сервером
- [ ] Офлайн-режим: собранное читается и ищется без сети; действия (пометки,
      перемещения) складываются в очередь и уходят при появлении связи
- [ ] Отмена последнего действия — перемещение и удаление обратимы, пока письмо
      в корзине
- [ ] `IDLE` с откатом на опрос, переподключение при разрыве
- [ ] Тест: очередь офлайн-действий переживает перезапуск и не применяется дважды

**Приёмка:** письмо приходит мгновенно; папками и флагами можно пользоваться как
в обычном почтовике; без сети приложение остаётся рабочим.

## П5. Отправка: черновики, ответы, подписи

**Что меняется:** полноценное написание письма. С жёстким ограничением инварианта
П-1: **отправляет только человек, только кнопкой.**

**Зависит от:** П2

- [ ] Миграция `016`: `mail_draft` (ящик, кому, копия, тема, текст, вложения,
      `in_reply_to`, автор черновика: человек или помощник), `mail_identity`
- [ ] `integrations/mail/smtp_client.py`: отправка по SSL/STARTTLS, корректные
      `In-Reply-To`/`References` — иначе ответ прилетит клиенту отдельным письмом,
      а не в его же ветку
- [ ] Написать, ответить, ответить всем, переслать; цитирование с шапкой в
      принятом виде
- [ ] Несколько личностей на ящик (адрес, имя, подпись) — типично, когда с одного
      ящика пишут от себя и от отдела
- [ ] Подписи с подстановкой; шаблоны ответов переиспользуют `bots/templating.py`
- [ ] Вложения: выбор файлов, суммарный размер с предупреждением на 20 МБ;
      проверка «в тексте написано „во вложении“, а вложения нет»
- [ ] Автосохранение черновика, синхронизация с папкой черновиков на сервере
- [ ] Копия отправленного кладётся в `Sent` через `IMAP APPEND` — иначе в Outlook
      отправленного письма не будет и история разъедется
- [ ] LLM-черновик ответа (если включён): результат **всегда** в черновик, видно,
      кто автор — человек или помощник
- [ ] Перед отправкой — итоговое окно: получатель, тема, вложения, первые строки.
      Один экран, который нельзя проскочить. Предупреждение при более чем
      5 получателях (защита от «ответить всем» по рассылке)
- [ ] `tests/test_mail_send.py` с поддельным SMTP: заголовки цепочки верные,
      автоотправки нет ни на одном пути (проверяется как инвариант, как в С4)

**Приёмка:** ответ пишется и уходит из приложения; ни один автоматический путь не
отправляет письмо.

## П6. Ярлыки и скоростной триаж

**Что меняется:** ярлыки на цепочках и режим разбора почты с клавиатуры.

**Зависит от:** П2

Приоритет здесь заявлен явно — **скорость навешивания ярлыка**. Значит, целевое
действие это не «открыть меню → выбрать пункт → подтвердить», а одно нажатие
клавиши. Раскладка в духе почтовых клиентов, к которым привыкли: `J`/`K` —
следующая и предыдущая цепочка, `1`…`9` — ярлык с соответствующим номером, `E` —
в архив, `L` — завести заявку (после П9), `R` — ответить, `/` — поиск. Цифра
назначается ярлыку при создании и видна рядом с названием, чтобы её не приходилось
помнить.

- [ ] Миграция `017`: `mail_label` (имя, цвет, горячая цифра, порядок),
      `mail_thread_label` (составной первичный ключ — ярлык на цепочке либо есть,
      либо нет, дублей быть не может)
- [ ] Ярлык на **цепочке**, а не на письме: помечается разговор с клиентом,
      а не отдельная реплика
- [ ] Панель ярлыков в строке цепочки: цветные плашки, клик по плашке снимает
      ярлык — без диалога подтверждения (ошибочное снятие возвращается тем же
      кликом, диалог тут дороже ошибки)
- [ ] Режим триажа: полноэкранный разбор непрочитанного, одна цепочка на экране,
      подсказка по клавишам внизу, счётчик «осталось N»
- [ ] Массовое действие: выделение с `Shift`, ярлык на всё выделенное одним
      нажатием
- [ ] Ярлыки отражаются в IMAP-ключевые слова, где сервер их поддерживает, —
      тогда они видны и в Outlook
- [ ] Набор по умолчанию: «Заказ», «Запрос КП», «Счёт», «Срочно», «Рассылка»,
      «Личное»
- [ ] `tests/test_mail_labels.py`: ярлык не дублируется, снятие работает, удаление
      ярлыка снимает его со всех цепочек и не оставляет сирот

**Приёмка:** сто непрочитанных писем разбираются клавиатурой, не трогая мышь.

## П7. Скоринг писем и уведомления

**Что меняется:** приложение начинает отличать письмо с запросом от рассылки и
говорить об этом.

**Зависит от:** П1, П3

Ядро — чистая функция в `core/mail_triage.py`, без sqlite, Qt и сети: на входе
разобранные поля письма, текст вложений, справочник направлений и настройки, на
выходе — **балл, категория и список причин**. Причины обязательны: экран
показывает, почему письмо сочтено запросом, и пользователь правит правила, видя
логику, а не подбирая её вслепую. Это же делает функцию тестируемой без базы.

| Сигнал | Вес |
|---|---|
| Ключевое слово направления в теме, теле **или во вложении** | +40 |
| Запросные обороты: «пришлите КП», «стоимость», «наличие», «объём» | +25 |
| Вложение с признаками заявки (`заявка`, `спецификация`, таблица) | +20 |
| Отправитель или его домен уже есть в заявках | +15 |
| Письмо — ответ в существующей цепочке с нами | +15 |
| Стоп-слово направления («вакансия», «резюме», «реклама») | −30 |
| Признаки массовой рассылки: `List-Unsubscribe`, `Precedence: bulk` | −40 |
| Адрес вида `noreply@`, `no-reply@`, `notification@` | −35 |

- [ ] `core/mail_triage.py`: `score(fields, attachments_text, directions, settings)
      -> (score, category, reasons)` — чистая, покрыта тестами без базы
- [ ] Категории: `запрос` · `заказ` · `счёт` · `рассылка` · `прочее`
- [ ] Порог уведомления настраивается; по умолчанию 50
- [ ] Уведомление в трее через существующий `notify()`: тема, отправитель, ящик.
      Клик открывает цепочку
- [ ] Защита от лавины: не больше N уведомлений за проход (та же логика, что у
      `max_reminders_per_tick` в С4), остальное — счётчиком
- [ ] Скоринг применяется и к уже собранным письмам — кнопка «Пересчитать», как
      `rescan()` у наблюдения за словами
- [ ] Экран «Почта → Разбор»: правила, веса, порог и **проверка на живых письмах** —
      последние 50 с баллом и причинами, чтобы настройка была видимой, а не на веру
- [ ] Необязательный второй проход LLM **только для спорных** (балл 40–60):
      дешевле, чем гнать каждое письмо, и работает там, где правила бессильны.
      Выключен по умолчанию, инвариант П-5
- [ ] `tests/test_mail_triage.py`: рассылка с `List-Unsubscribe` не проходит порог
      даже с ключевым словом; ключевое слово направления плюс запросный оборот —
      проходит; стоп-слово перевешивает

**Приёмка:** из реального потока почты запросы всплывают наверх, а рассылки не
звонят в трей.

## П8. Виджет на рабочем столе

**Что меняется:** отдельное окно поверх всех, показывающее почту, сбор и ботов, —
чтобы не открывать приложение ради «что нового».

**Зависит от:** П7 (намеренно не П5 и не П9 — виджету нужны письма и их баллы,
но не отправка и не заявки; сессию можно двигать вперёд)

Технически это обычное окно Qt с флагами `Qt.FramelessWindowHint |
Qt.WindowStaysOnTopHint | Qt.Tool` (последний убирает его из панели задач).
Полностью портативно, никакого установщика — в отличие от панели виджетов
Windows 11, которая требует упакованного MSIX и нарушает инвариант 1.

- [ ] `ui/widget_window.py`: перетаскивание за любую точку (своя обработка
      `mousePressEvent`/`mouseMoveEvent` — рамки-то нет), позиция и размер в
      `app_settings`, восстановление при запуске
- [ ] Три сворачиваемые секции, каждая отключается отдельно:
      - **Почта** — новые письма списком: цветная метка ящика, отправитель, тема,
        точка непрочитанного, подсветка запросов по баллу, скрепка при вложениях
      - **Сбор** — `LiveChart` со скоростью сбора (виджет уже есть в
        `ui/widgets.py`, писать нечего), число чатов в работе, ошибки
      - **Боты** — состояние, `ActivityBars` по активности за неделю, число новых
        заявок
- [ ] **Ярлык в один клик прямо из виджета** — заявленный приоритет: строка письма
      разворачивается в ряд цветных кнопок ярлыков, нажатие применяет и
      сворачивает. Открывать приложение не нужно
- [ ] Клик по письму открывает главное окно на этой цепочке
- [ ] Прозрачность настраивается; режим «только почта» для узкой полосы сбоку
- [ ] Закрытие прячет в трей, пункт меню трея «Показать виджет»
- [ ] Виджет читает из базы и ничего не опрашивает сам
- [ ] Виджет добавляется в смоук-тест: открывается офскрин без падения

**Приёмка:** виджет висит в углу экрана, показывает все ящики сразу и позволяет
разметить письмо, не разворачивая приложение.

## П10. Фильтры, адресная книга, отчёты по каналам

**Что меняется:** оставшееся от полноценного почтовика плюс главный ответ на
вопрос, ради которого воронки разделялись.

**Зависит от:** П4, П9

**Фильтры — но безопасные.** Полный клиент без правил неполон, а тихо
похороненное письмо от клиента дороже любой экономии. Поэтому: фильтр **никогда
не удаляет**, каждое срабатывание пишется в журнал и отменяется одной кнопкой,
а если фильтр убрал письма из «Входящих» — над списком висит счётчик «фильтры
спрятали N писем» со ссылкой. Ничего не исчезает молча.

- [ ] Миграция `019`: `mail_filter`, `mail_filter_log`, `mail_contact`
- [ ] **Сводный отчёт по каналам**: сколько заявок пришло, сколько дошло до
      сделки, конверсия и средний срок — по каждому каналу, за период. Работает
      поверх `funnel_stage.kind`, поэтому честно сравнивает воронки с разными
      этапами
- [ ] Разрез «канал × направление»: видно, что упаковка идёт с биржи, а сырьё —
      почтой
- [ ] Условия фильтров: отправитель, домен, тема, текст, наличие вложения,
      размер, ящик. Действия: ярлык, папка, пометка, «не уведомлять» — без
      удаления
- [ ] Адресная книга: собирается из истории переписки, автодополнение при
      написании, ручные записи и группы, импорт и экспорт CSV
- [ ] **Менеджер вложений** — все присланные файлы одним списком с поиском по
      имени, типу, отправителю и дате
- [ ] Отчёт «скорость ответа»: среднее и худшее время до нашего первого ответа,
      по ящикам и направлениям. Строится на `mail_message.is_outgoing`
- [ ] Ретеншн для почты: срок хранения, архив в JSONL перед удалением, отдельный
      срок для вложений — переиспользует `retention_service` целиком
- [ ] Экспорт переписки в существующие форматы
- [ ] `tests/test_mail_reports.py`

**Приёмка:** видно, по каким каналам приходят клиенты, какой канал конвертируется
лучше и за сколько часов мы в среднем отвечаем.

### Что предложено сверх запрошенного и почему

Запрошенное — разбор почты, уведомления, поиск, цепочки, несколько ящиков,
виджет, быстрые ярлыки, просмотр вложений, полный функционал клиента, раздельные
воронки — распределено по С10 и П1–П10. Сверх этого предложено пять вещей;
каждая появилась из чтения кода, а не из общих соображений.

1. **Поиск по содержимому вложений (П3).** Раз текст из PDF, Word и Excel всё
   равно извлекается для скоринга, он почти бесплатно попадает в тот же индекс
   FTS5. Письмо находится по строке из присланного прайса.
2. **Разбор вложенной заявки в поля (П9).** Раз просмотрщик уже умеет читать
   таблицу и PDF, заполнение полей — это сопоставление колонок, а не новая
   подсистема.
3. **Напоминание «клиент написал, мы молчим» (П9).** Механизм напоминаний уже
   построен в С3 и смотрит только в свою сторону — «мы написали, он молчит».
   Обратное направление ловит более дорогую ошибку и стоит нескольких строк
   поверх готового сервиса.
4. **IMAP IDLE вместо опроса (П4).** Письмо появляется мгновенно, а не через
   несколько минут. Для почты, где половина ценности — успеть ответить первым,
   это заметная разница.
5. **Менеджер вложений и отчёт по скорости ответа (П10).** «Где тот прайс за
   март» перестаёт быть раскопками в переписке; скорость ответа — единственная
   метрика продаж, которую приложение сможет считать честно, без ручного ввода.

## Осознанно не делаем

Чтобы не возвращаться к этим вопросам.

| Не делаем | Почему |
|---|---|
| Графовая модель сценария с 7 типами узлов | Ветвление работает и покрыто тестом. Роль `delay`/`condition`/`handoff` играют триггеры `inactivity`, `schedule` и действие `notify_manager` |

Найдено и исправлено по дороге: стиль Qt не был закреплён — на Windows 11 заливка
выбранных кнопок не работала, а на Linux выглядела правильно; перестройка

### С1 — готова

**Миграции.** `db/migrations.py` — трекнутый список шагов вместо одной
идемпотентной функции. Старое поведение (весь `migrate()`, каким он был
до этой сессии) стало шагом «006» с флагом `self_healing=True` — он, как
и раньше, выполняется на каждом запуске независимо от того, что уже
отмечено применённым, потому что его собственные проверки внутри
(`_column_exists` и т.п.) сами по себе идемпотентны. Всё, что добавляется
после 006, — обычный одноразовый шаг: выполняется один раз, помечается в
`schema_migrations`, дальше не трогается — иначе откат немедленно
переприменялся бы на следующем запуске.

Решение по откату из плана подтверждено практикой: `down()` пишется только
там, где это один `DROP TABLE`/`ALTER`; общую защиту даёт обязательный
бэкап перед первым применением новой миграции к уже существующей базе
(`Database._backup_before_migration`, тот же `sqlite3 backup API`, что и у
`BackupService.backup_to`, — не сам `BackupService`, потому что на этом
шаге ещё нет мигрированной `Database`). На чистой установке бэкап не
создаётся — защищать нечего.

**Справочник направлений** — таблица `direction`, CRUD в `database.py`,
экран «Направления» в общих пунктах меню (общий для «Сбор» и «Боты»).
Список, порядок (↑/↓, перезапись `order_index`), редактирование через
диалог, экспорт/импорт в JSON (merge или полная замена, битые записи
пропускаются, а не роняют импорт).

**Найдено и исправлено по дороге, не входило в план:** таблицы с кнопками
в ячейках (`setCellWidget`) обрезали текст «Изменить»/«Удалить» до
нечитаемого вида на трёх экранах — новом «Направления», а также в уже
существующих «Наблюдение» и «Настройки → выгрузка по расписанию».
Причина: `resizeColumnsToContents()` меряет текст `QTableWidgetItem`, а не
`sizeHint()` виджета в ячейке, и без явной ширины колонка получалась уже
кнопки; `QPushButton` при этом не эллипсирует текст, а обрезает по центру
с обеих сторон, поэтому терялись именно первые буквы («Изменить» →
«зменить»). Поставлена явная ширина колонок с запасом над `sizeHint()`.
Отдельного отчёта не поднимал — правки однострочные, три файла, тот же
корень причины.

**Тесты:** `test_migration.py` расширен (учёт применённых миграций,
наличие `direction`), новые `test_migration_backup.py` (бэкап создаётся
один раз и только когда есть что защищать; откат снимает ровно
добавленное) и `test_directions.py` (CRUD, порядок, экспорт/импорт,
устойчивость к битым данным). 15 экранов открываются (было 14).

**Осталось на будущее, не блокирует С2:** `_backup_before_migration`
живёт в `Database`, а не в `BackupService`, сознательно — см. комментарий
в коде про цикличность. Если в С2+ понадобится показать бэкапы миграций
пользователю (не только в `data/backups/pre_migration/`), это отдельная
маленькая задача, не переделка.

### С2 — готова

**Домен.** `core/lead.py` — первый модуль в `core`, коды статусов остались
английскими/snake_case (как везде в схеме — `chats.status`, `bots.status`,
`bot_scenarios.kind`), русский только в словаре меток. «Допустимые
переходы» на практике оказались одним правилом: в «отказ» нельзя без
причины, всё остальное (пропуск стадий, возврат назад) не запрещено — у
одного человека без второго менеджера некому делать переходы, которые
стоило бы проверять. Цвета статус-пилюли (`STATUS_COLORS`) тоже переехали
сюда — это просто строки, не Qt-зависимость, а раньше дублировались бы
между списком лидов и карточкой.

**Миграция «008».** Расширяет `bot_leads` новыми колонками и добавляет
`lead_events`. Без `down()` — трогает не только схему, но и данные
(`status` старых заявок переписывается), поэтому это не однострочный шаг,
и защитой служит обязательный бэкап, а не откат. Ремап: `new → новый`,
`in_progress → переговоры` без вопросов; `closed → сделка` — с пометкой,
потому что старое «closed» означало и «продали», и «отказались», и это
единственное по-настоящему потерянное различие. Каждой перенесённой заявке
пишется событие `created`, бывшим «closed» — ещё и `status` с текстом
предупреждения. Идемпотентно: повторный прогон `migrate()` не плодит
вторые копии событий.

**Сознательно не перенёс из черновика плана в схему:** `score` (в плане
явно нет скоринга), `next_action_at`/`next_action_text` (это С3),
`crm_id`/`crm_synced_at` (С6/С7), `archived_at` (пока не нужен ни одной
сессии). Если понадобятся раньше срока — добавить колонку одной новой
миграцией, а не переделывать эту.

**Репозиторий и карточка.** `Database.add_lead` расширен новыми полями
(старые позиционные вызовы работают без изменений — заведён отдельный
тест на обратную совместимость), `set_lead_status` — единственный путь
смены статуса, всегда через `core.lead.validate_transition` и всегда с
записью в `lead_events`. `lead_card.py` — карточка с полями, историей,
вкладкой переписки (по `sender_id` через уже собранные сообщения) и
вложениями КП (просто список путей в JSON-колонке, без своего файлового
стора). Список лидов (`leads_tab.py`) — чипы фильтра теперь строятся из
`core.lead.ALL_STATUSES`, двойной клик и пункт меню открывают карточку.

**Найдено и исправлено по дороге, не входило в чек-лист сессии, но было
прямым следствием смены вокабуляра статусов:**
- `leads_tab.py._on_cell_clicked`/`_on_undo` (быстрая смена статуса по
  клику на пилюлю) писали статус напрямую через `set_lead_field`, в обход
  `set_lead_status` — новый статус применялся бы, но без записи в историю,
  то есть без выполнения собственного критерия приёмки этой же сессии.
  Исправлено до коммита, самостоятельно, до пользователя не доходило.
- `leads_tab.py._reassign` через `set_lead_field` жёстко ставил старый код

  переназначение менеджера больше не трогает статус вообще.
- `ui/screens/today.py` считал «в работе» по старому коду `in_progress` —
  после миграции такого значения в базе никогда не появится, счётчик тихо
  показывал бы 0. Исправлено на объединение `qualified`/`quote_sent`/
  `negotiation`, как в `leads_tab.py`.
- `bots/export.py` — Excel-выгрузка лидов держала свой собственный
  `_STATUS_LABELS` с тремя старыми кодами; новые статусы выгружались бы
  сырым кодом (`qualified`) прямо в файл для менеджера. Переведено на
  `core.lead.label_for_status`.
- `Database.leads_funnel()` (сводка на экране «Аналитика») группировала по
  старым трём кодам — «в работе» и «закрыты» стали бы вечными нулями.

Проверено, что не задето: `main_window.py` (счётчик новых лидов сравнивает
с `"new"` — это валидный код и в новой модели, без изменений), `list_tab.py`,

**Тесты:** `test_core_no_qt.py` (AST-проверка на отсутствие Qt/Telethon/

### С3 — готова

**Миграция «009».** Два независимых изменения в одном шаге: колонки
`next_action_at`/`next_action_text`, и снятие `NOT NULL` с `bot_leads.
contact_id`/`bot_id` — до этой сессии каждый лид обязан был прийти от
бота, а «завести откуда угодно» означает, что теперь бывает и лид без
бота, и лид без привязанного контакта. SQLite не умеет снимать
ограничение колонки на месте, поэтому таблица перестраивается тем же
способом, что уже был в `_migrate_scenario_sessions_unique` (копия →
drop → rename → переиндексация) — не новая идея, а второй случай того
же приёма. Собственных полей лида (display_name/phone/tg_user_id и
так далее, С2) достаточно, чтобы карточка и списки показывали лид без
`contact_id` не хуже, чем с ним.

**Наступил на то же грабли, что предупреждал в комментарии.** Список
колонок перестройки фиксирован на момент миграции; я сначала дописал
`ALTER TABLE ADD COLUMN next_action_at/next_action_text`, а потом
вызвал перестройку — которая тут же выбросила обе только что
добавленные колонки, потому что копирует по своему жёсткому списку.
Нашёл сразу же, тестом (`next_action_at` не находилась при первой же
попытке `set_lead_field` в `test_lead_lifecycle.py`), поменял порядок:
сначала перестройка, потом добавление новых колонок — как и было
написано в докстринге функции, просто не в том порядке, в котором я
сам её вызвал.

**Заведение «откуда угодно» — три пути, все через `add_lead` с
`contact_id=None, bot_id=None`:**
- Вручную: кнопка «＋ Новая заявка» на экране лидов → `NewLeadDialog`
  (новый файл `lead_create_dialog.py`) → сразу открывается обычная
  карточка для остального.
- Из найденного сообщения: кнопка «Создать лид» на карточке сообщения
  в «Собранном», и пункт контекстного меню на строке в «Наблюдении».
  Оба берут identity прямо из строки сообщения (tg_user_id/username/
  display_name/chat_id) — без создания `bot_contacts`-записи: у лида
  уже есть свои поля для этого с С2, плодить контакт не от бота незачем.
- Из сценария: другое решение, чем в черновике плана — не отдельное
  действие `create_lead` в редакторе правил, а сопоставление на уровне
  шага сценария. У каждого шага теперь есть необязательное поле
  «→ поле лида» (`scenario_screen.py`, `step["lead_field"]`, восемь
  значений — `core.lead.SCENARIO_LEAD_FIELDS`, без направления: тому
  нужен id из справочника, а не текст ответа). `content` по-прежнему
  получает сырые ответы целиком — сопоставление только дополняет, не
  заменяет, несопоставленное поле не пропадает. Расхождение с
  формулировкой плана раскрыто явно; причина — сама генерация лида по
  завершении сценария и так уже не была отдельным «действием» в
  редакторе правил (это встроенное поведение `run_scenario`/
  `continue_scenario`), а плодить настоящее отдельное действие ради
  того же самого результата не стоило лишнего слоя.

**Напоминания.** `LeadReminderService` — тот же тик-цикл на asyncio, что
у `ExportScheduleService`, раз в 60 секунд, «прошло время — а не сейчас
ли ровно тот час» (переживает уснувшую машину). Дедупликация — не
отдельный флаг, а сам факт очистки `next_action_at`/`next_action_text`
при срабатывании: `due_lead_reminders()` смотрит только на это поле,
так что повторный тик (и тем более новое соединение с базой после
рестарта) просто не находит уже сработавшее напоминание. Запись в
`lead_events` (`kind=reminder`, ранее объявлен в С2, но не использовался)
остаётся постоянным следом даже после очистки поля. Показ — тот же
`TrayController.notify`, что у совпадений в «Наблюдении».

**Список и воронка.** `list_leads()` — новые необязательные фильтры
`direction_id`/`source_type`/`since`/`until`, обратная совместимость
не пострадала (позиционные `bot_id`/`status` не тронуты). Воронку не
стал делать отдельным виджетом: чипы фильтра статуса и так кликом
проваливаются в список, им просто дописан счётчик (`leads_status_
counts()`, одним `GROUP BY`) — то же требование («сколько на каждом
статусе, клик проваливается в список»), без дублирующего бруска рядом.

**Блок «Лиды» в навигации.** `main_window.py`: `BLOCKS` — третий пункт,
`NAV_BY_BLOCK["leads"]` — экран `leads` переехал туда из `bots`.

### С4 — готова

**Что уже было, а что действительно новое.** Прежде чем строить, проверил
по факту: пауза с разбросом между отправками, кулдаун на контакт и
FloodWait (продление паузы, а не повтор с нуля) уже существовали в
`userbot_runner.make_send` и были покрыты `test_send_limits.py`. Но
**только там** — у `BotApiRunner.send_dm` (aiogram, Bot API) не было вообще
никакой защиты: ни паузы, ни кулдауна, ни лимитов, только тот же
FloodWait-ретрай. Двух раздельных путей отправки без общего слоя — и
есть та причина, по которой это сессия С4, а не мелкая правка.

**`bots/outbox.py`, не `services/telegram/outbox.py`.** Отклонение от
черновика плана: outbox должен оборачивать `make_send`/`BotApiRunner.
send_dm` и читать `bots.settings` — оба уже живут в `bots/`, и
`services/` в этом приложении ни разу не тянется в `bots/` (только
наоборот). Заводить новый вложенный пакет `services/telegram/` только
ради буквального пути значило бы придумывать структуру, которой больше
нигде в проекте нет.

**`reactive` — единственное, что нельзя вывести из пары (target, text).**
Обёртка `Outbox.wrap(bot_id, raw_send, reactive=...)` решает, что
происходит с сообщением, но «это ответ на входящее или сообщение по
инициативе бота» ниоткуда не следует из самих аргументов — это должен
сказать вызывающий код. Реактивно: `RulesEngine.fire`/`continue_scenario`,
вызванные из `_handle_new_message`/`_handle_message` обоих раннеров
(контакт только что написал) и повторная отправка черновика по клику
(`BotManager.send_draft` — человек только что решил). Проактивно: то же
самое, но вызванное из `TriggerScheduler` (`schedule`/`inactivity` —
никто ничего не писал). Тихие часы и персистентный (в днях, не в
секундах) кулдаун на контакт действуют только на проактивные — отвечать
человеку, который только что написал, в три часа ночи не грех, а вот
самим писать в три ночи — грех. Лимит в час/сутки и лимит первых
сообщений в сутки действуют на оба пути: всплеск ответов на входящие
тоже может выглядеть как спам.

**Холодное первое сообщение → черновик, не отправка.** Если это
проактивная отправка и `outbox_sends` не хранит ни одной строки
`status='sent'` для этой пары (бот, адресат) — это первое сообщение,
и при выключенном `auto_send_cold` (по умолчанию) оно уходит в
`outbox_drafts`, `raw_send` не вызывается вообще. Экран «Боты» получил
панель «Черновики» — единственное место, откуда они уходят, по кнопке.
Включение `auto_send_cold` в `SendLimitsDialog` спрашивает подтверждение
через `QMessageBox` — ровно предупреждение, которого просит инвариант 6.

**Дедупликация лимитов — своя таблица, не `bot_activity_log`.**
`bot_activity_log` пишет только входящие события (`trigger_fired`) и
пару специальных меток планировщика — ни одной реальной попытки
отправки там никогда не логировалось. `outbox_sends` — новая таблица
именно для этого: каждая попытка (sent/blocked/dry_run), с флагом
`is_first`, откуда считаются часовой/суточный лимиты, лимит первых
сообщений и «когда мы в последний раз писали этому контакту» —
персистентно, без in-memory состояния, переживает рестарт (проверено
тестом на новом соединении с базой, тот же приём, что у С3-напоминаний).

**Что сознательно упрощено:** чёрный список и все лимиты — на бота, не
на Telegram-аккаунт целиком (несколько ботов на одном аккаунте не
складывают лимиты друг с другом). Решение по аналогии с уже
существующим `bots.settings` — тоже на бота, не на аккаунт; полноценная
привязка к `account_id` не по плану буквально и не стоила лишнего слоя
в рамках одной сессии.

**Не сделано из-за журнала «что уже есть»:** карта сессий отмечала
`ui/screens/settings.py` (1036 строк) на разрезание «в С4 и С6» — этот
файл в этой сессии не тронут вообще, новый интерфейс (лимиты, тихие
часы, чёрный список, черновики) целиком лёг в уже существующий диалог
на боте (`SendLimitsDialog`) и новую панель под списком ботов, а не в
`settings.py`. Разрезание `settings.py` остаётся на С6 или отдельной
мелкой задачей — не забыто, просто не понадобилось для этой сессии.

**Тесты:** `test_outbox.py` (новый) — dry-run не пропускает ничего,

**Формат и загрузчик.** `presets/*.json` — плоский файл на пресет,

`{текст}` в вопросе, либо усложнять `render()` понятием «уже
подставлено» — двойные скобки проще обоих вариантов.

отвечать в личку всегда можно сразу, а сообщение в чат теперь то же

### С6 — готова

**Явное отклонение от формулировки сессии, раскрыто сразу.** «Что
меняется» этой сессии в плане звучит как «лид уходит в CRM сам» —
это подразумевает автоматику. Собственный чек-лист С7 при этом
отдельным пунктом называет «что и когда отправлять: только
квалифицированные, или все, или по кнопке» — то есть политика
автоотправки прямо отписана следующей сессии. Возможности сделать и то,
и другое в одной сессии не было — ядро (очередь, ретраи, дедуп,
маппинг полей) само по себе большая задача. Выбрал ядро: С6 отправляет
**только по кнопке** на карточке лида, никакого триггера «лид стал
quote_sent → само улетело» пока нет. Это ровно то же самое разделение,
что и в С4/С5 (outbox — лимиты и черновики; кто именно и когда шлёт —
решает вызывающий код), просто проведено на сессию раньше срока по
необходимости, а не по плану дословно.

**Хранение учётных данных.** Входящий вебхук — одна строка
(`https://портал/rest/user_id/token/`), а не разбор на
портал/user_id/token по отдельности: URL уже самодостаточен, разбирать
и собирать обратно значило бы гонять шанс ошибиться в порядке слэшей
без всякой выгоды. Шифруется через уже существующий
`SecurityService.encrypt_secret`/`decrypt_secret` (тот же путь, что у
токенов ботов) — `bots/crypto.py`'s `encrypt_token`/`decrypt_token`
оказались настолько общими, что не потребовалось даже копировать их
форму: `integrations/bitrix.py` использует `SecurityService` напрямую.
Хранится через уже существующий `app_settings` (`get_setting`/
`set_setting`), не новая таблица — одна связка на приложение, второй
портал никому не нужен (инвариант 5). Ключ ротации
(`register_bitrix_rotation`) — копия по духу `register_bot_token_
rotation`, чтобы смена мастер-пароля не превращала сохранённый вебхук
в нечитаемую кашу молча.

**Очередь.** `crm_queue` — `UNIQUE(lead_id)`: повторная постановка в
очередь уже поставленного лида просто сбрасывает `next_attempt_at` на
«сейчас», а не плодит вторую строку. Ни одна попытка отправки не
роняет запись из очереди, кроме успеха — экспоненциальный backoff
(60с → потолок 30 мин) растёт при каждой неудаче, но никогда не
«сдаётся»: «сети нет» и «Bitrix отклоняет данные» с точки зрения
очереди выглядят одинаково — оба раза это просто «ещё не отправлено»,
что и требует приёмка («лиды не теряются»). Различать эти два случая
для пользователя — это уже «журнал синхронизации», прямо в чек-листе
С7, не подмена его здесь.

**Дедупликация — не «не создавать дубль», а «дописать в найденный».**
`crm.duplicate.findbycomm` по телефону, потом по email; если Bitrix
нашёл существующий LEAD, локальный `crm_id` привязывается к найденному
без вызова `crm.lead.add` вообще — ничего не создаётся и не
обновляется на стороне Bitrix, просто отмечается связь. Дальше при
следующей отправке (лид отредактировали) `crm_id` уже есть →

явный пункт С7 («значения тянутся из `crm.status.list`»), не

**Первый прямой сетевой вызов в приложении.** До этой сессии никакой

### С7 — готова

**Маппинг статусов — один словарь на всё приложение, не колонка.**
`{статус ChatGrab: STATUS_ID Bitrix}` живёт как обычный JSON в
`app_settings` (`bitrix.STATUS_MAP_KEY`), тем же путём, что и любая
другая настройка приложения — это не атрибут конкретной строки
(лида/направления), а одна связка на портал, и по инварианту 5 второго
портала не бывает. Маппинг направлений, наоборот, лёг колонкой
(`direction.crm_source_id`, миграция «012», без `down()` — тот же
случай, что 008/009/011: `ALTER` на существующей таблице, а не
самостоятельное добавление, которое можно чисто снять) — это
действительно атрибут конкретного направления, ровно как `price_file`
или `keywords` рядом с ним.

**`crm.status.list` — один метод на обе сущности.** `BitrixClient.
list_statuses(entity_id)` вызывает его с `filter.ENTITY_ID = "STATUS"`
для стадий лида и `"SOURCE"` для источников — Bitrix использует общий
формат ответа (`STATUS_ID`/`NAME`) для обоих, так что дублировать метод
не потребовалось, только два разных экрана-вызова с разным
`entity_id`. Оба выпадающих списка на экране Bitrix24 остаются
рабочими и без обращения к порталу — если значение уже сохранено, но
не входит в свежесгруженный список (портал недоступен, или значение
проставлено руками), оно всё равно остаётся выбранным пунктом
«(текущее значение)», а не молча теряется.

**Явное отклонение от буквальной формулировки.** Чек-лист говорит
«маппинг… настраивается в UI» применительно к направлению → полю лида
в Битрикс, но в Bitrix24 REST это не одно поле, а два независимых:
`STATUS_ID` (стадия) и `SOURCE_ID` (источник) — они и разведены по двум
отдельным блокам экрана, привязанным к разным сущностям ChatGrab
(статус лида и направление соответственно), а не к одному общему
списку «поле → значение». Это точнее исходной формулировки, не проще
её.

**Что и когда отправлять — политика опроса, а не хук на каждое
изменение лида.** Три значения (`manual`/`qualified`/`all`,
`bitrix.AUTO_SEND_*`) хранятся так же, как маппинг статусов — одна
строка в `app_settings`, по умолчанию `manual` (свежая установка с
только что вставленным вебхуком не должна начинать раздавать лиды в
CRM до того, как настроено, что именно отправлять). Реализовано как
фаза в начале каждого тика `BitrixSyncService.tick()`
(`_auto_enqueue`), а не как обработчик на `set_lead_status`/
`set_lead_field`: у хука было два способа появиться — либо `db/`
дергает `services/` напрямую (нарушает правило слоёв, которое уже
дважды всплывало в С4 и держится с тех пор: `db/` не импортирует
`bots/`/`services/`), либо каждое место, меняющее статус лида
(карточка, сценарий, правило, будущая интеграция), само вызывает
`bitrix_sync_service.enqueue()` — тогда пропущенный вызов в одном месте
молча ломает автоотправку именно там. Опрос раз в тик (≤30 секунд)
стоит одного дешёвого запроса и находит те же заявки, что нашёл бы
хук, просто на несколько секунд позже — цена, которую эта сессия
предпочла риску молчаливо забытого места. Сам SQL-запрос —
`db.leads_due_for_auto_crm_sync(statuses=None)` — намеренно ничего не
знает о политике (только «эти статусы или любой»): что конкретно
считается «квалифицированным» (`QUALIFIED`/`QUOTE_SENT`/`NEGOTIATION`/
`WON`, не `NEW` и не `LOST`) решает `bitrix_sync_service.py`, не `db/`
— та же граница ответственности, что и в `outbox_counts()` из С4.
Условие «нуждается в отправке» — `crm_id IS NULL OR crm_synced_at IS
NULL OR crm_synced_at < updated_at`: это шире буквального «ещё не
уходила» и означает, что уже отправленный, но затем изменённый лид
(например, статус ушёл дальше по воронке) тоже переставится в очередь
и переотправится `update`'ом — без этого второй пункт чек-листа
(маппинг статусов) не имел бы смысла для авто-отправки: STATUS_ID
менялся бы только у той единственной попытки, что случилась в момент
первой синхронизации.

**Журнал синхронизации — тоже без новой таблицы, тем же приёмом, что
задумывался в С6.** `db.crm_sync_journal()` объединяет
`lead_events(kind='sync')` (успешные отправки, пишет `log_crm_sync` ещё
с С6) и то, что прямо сейчас лежит в `crm_queue` (ожидает или падает
с `last_error`) в одну ленту, отсортированную по времени. Отдельная
таблица под «журнал» дублировала бы данные, которые обе части системы
и так уже пишут — тому же принципу, которым план заранее просит
руководствоваться и в С8 («Зависит от… — считается по `lead_events`»,
не отдельный кеш).

**Резка `settings.py`.** Раздел «BITRIX24» (карточка вебхука, статус,
кнопки сохранить/проверить) вынесен в новый `ui/screens/
bitrix_screen.py` целиком, с добавлением маппинга/политики/журнала —
в `settings.py` он был явно помечен как временный ещё в С6 («…moves to
its own screen in С7»). На старом месте осталась короткая
карточка-указатель со ссылкой на новый экран — не пустое место, а
явная подсказка, куда переехало. Экран подключён в `main_window.py`
как `COMMON_ITEMS`, а не отдельный `BLOCKS`-раздел: он не привязан ни
к «Сбору», ни к «Ботам», ни к «Лидам» конкретно, ровно как
«Подключение»/«Направления»/«Настройки» рядом с ним.

**Тесты:** `test_bitrix_mapping.py` (новый) — маппинг статусов
сохраняется и пустые значения не протаскиваются; `lead_fields()`
подставляет `STATUS_ID` для замапленного статуса и просто не добавляет
поле для незамапленного (не падает); `SOURCE_ID` берётся из
`direction.crm_source_id`, откатываясь на `"OTHER"` и для немапленного
направления, и для отсутствующего (`None`) — тот самый случай из
чек-листа «неизвестное направление не роняет отправку»; политика
`manual` не ставит ничего в очередь сама; `qualified` пропускает лида
на `NEW`, но подхватывает того, кто дошёл до `NEGOTIATION`; `all`
подхватывает и `NEW`; журнал возвращает хотя бы одну запись с
`outcome == "ok"` после успешной отправки. `test_bitrix_sync.py` (С6)
прогнан как есть и не потребовал правок — политика по умолчанию
`manual`, так что новая фаза `_auto_enqueue` в начале `tick()` для него
молчит, ровно как и должна. `test_migration.py`/`test_migration_backup.
py` обновлены под миграцию «012» (та же логика отката, что и
008/009/011 — без `down()`, откат пропускает её и находит «007»);
добавлена проверка, что колонка `direction.crm_source_id` действительно
появляется. 16 экранов по-прежнему открываются (был 15, добавился
`bitrix`).

Состояние: схема v12 (миграции 006–012), 31 тест-файл + смоук, обе
задачи CI на очереди на подтверждение (Linux/Windows), exe должен
собраться и запуститься.

### С8 — готова

**Никакой новой таблицы под отчёт — тот же приём, что и «журнал
синхронизации» в С7.** Все четыре цифры (по источникам, по направлениям,
срок до КП, причины отказов) — обычные `GROUP BY`-запросы поверх
`bot_leads`/`lead_events`, добавленные в `database.py` рядом с
`leads_funnel()`. Ничего не кэшируется отдельно: план сам просит именно
этого для С8 («считается по `lead_events`»), не только для журнала
синхронизации годом раньше.

**Одна и та же населённость лидов для всех четырёх цифр.** Все запросы
фильтруют по `bot_leads.created_at` (лид создан в периоде), а не по тому,
когда внутри периода случилось конкретное событие — иначе «конверсия по
источникам» и «причины отказов» описывали бы два разных множества лидов
за один и тот же период на экране. «Срок до КП» берёт `MIN(created_at)`
по `lead_events(kind='status', to_status='quote_sent')` — минимум, а не
последнее совпадение, на случай если лид откатился на более раннюю
стадию и снова дошёл до КП позже; при отсутствии совпадений в периоде
возвращается `None` («нет данных»), не `0` — у пустого множества нет
среднего.

**`core/lead_report.py` — одна чистая функция, не полноценный
report-модуль.** Единственное, что нужно было не продублировать между
таблицей на экране и листом в выгруженном .xlsx — превращение
total/won/lost в конверсию (`in_progress = total - won - lost`,
`conversion_pct = won / total`). Проходит `test_core_no_qt.py`
автоматически: тест обходит `core/*.py` через `glob`, отдельно
регистрировать новый файл не потребовалось.

**Экспорт — не новый движок, а третье значение в уже существующем
`ExportParams.kind`.** До этой сессии `ExportParams`/`ExportService`
знали только про выгрузку сообщений — сессия добавила `kind: "messages"
| "leads_report"`, с одним и тем же классом, одним и тем же
`save_preset`/`load_preset` (JSON `dataclass.__dict__`, старые сохранённые
пресеты без ключа `kind` как раньше получают дефолт `"messages"` при
распаковке `**data` — обратная совместимость без миграции пресетов) и
одним и тем же `export_schedule_service.py`. Буквально это и есть
«экспорт через существующее расписание выгрузок» из чек-листа: новый
экран «Отчёты» лишь собирает `ExportParams(kind="leads_report", ...)` и
жмёт «Сохранить как пресет» — пресет тут же виден в комбобоксе
«Настройки → Выгрузка по расписанию» безо всяких изменений в этом
экране, потому что тот комбобокс и так читает `db.list_presets()`
не глядя, что внутри `params`. Единственная реальная правка в самом
`export_schedule_service.py` — подпись в `last_result`/логе шла как
«N сообщений» безусловно; для лидового пресета это было бы враньём,
исправлено на «N лид(ов)» через `params.kind` (уже разобранный из
пресета к этому моменту, лишнего запроса не потребовалось).

**Явное расширение буквальной формулировки.** «Экспорт в лист» описан
чек-листом как один файл — получилось четыре листа в одной книге
(Источники / Направления / Сводка / Причины отказов) вместо одного
плоского листа: у каждой из четырёх цифр разная форма таблицы (два
среза по source/direction с одинаковыми колонками, один число, один
частотный список), сплющивать их в общий лист значило бы либо повторять
шапку четыре раза на одном листе, либо терять часть данных. Разные
листы одной книги решают это без выдумывания нового формата файла.

**UI.** Новый экран `ui/screens/reports_screen.py`, третий пункт блока
«Лиды» (после «Заявки») — не отдельный блок `BLOCKS`, потому что отчёт
без заявок под ним не нужен, ровно как «Отчёты» не имеет смысла как
раздел без «Боты» или «Сбор» рядом. Быстрый выбор периода — тот же
приём для `_DATE_RANGES`, что уже был в `leads_tab.py` (готовые
диапазоны + ручные поля дат поверх них, а не только один способ
выбрать период).

**Тесты:** `test_lead_reports.py` (новый) — `lead_report.conversion()`
как чистая функция; известный набор из 7 заявок (одна намеренно вне
периода) даёт ожидаемые total/won/lost по каждому чату и направлению,
включая NULL-корзины (без чата — от бота/вручную; без направления);
средний срок до КП сходится на заранее подставленных датах события
(2 и 4 дня → среднее 3.0); причины отказов группируются как ожидалось;
запрос за период без единого совпадения не падает и возвращает пустой/
нулевой результат вместо ошибки; `ExportService.run(kind="leads_report")`
строит все четыре листа с ожидаемым числом строк и совпадающим итогом
лидов; тот же сохранённый пресет реально запускается через

Состояние: схема v12 (без изменений — С8 ничего не меняет в схеме),

(Linux/Windows), exe должен собраться и запуститься.

### С9 — готова

**Заодно поправлена «Карта сессий» вверху файла** — таблица статусов у С7
и С8 всё ещё показывала «⬜ не начата» после того, как обе сессии были
закрыты (чек-листы отмечены, журналы написаны, CI зелёный) — обновление
статуса в этой сводной таблице выпало из тех двух сессий. Поправлено
заодно с С9, не отдельным коммитом: сама таблица не часть чек-листа С9,
но оставлять её врущей дальше не было смысла.

**Явное отклонение: одна зависимость превратилась в ноль.** «Оценка» С9 в
карте сессий с самого начала предполагала «1 зависимость» — по всей
видимости, SDK-клиент (`anthropic` или аналог). С6 уже установила
прецедент для ровно этой ситуации: «интеграция — это HTTP, а не SDK»,
когда `aiohttp` (первая и единственная прямая сетевая зависимость
приложения) оказалась достаточной для Bitrix24. Здесь то же решение
подходит ещё лучше: `integrations/llm.py` — три системных промпта поверх
одного REST-эндпоинта (`POST /v1/messages`), `LLMClient` по форме почти
точная копия `BitrixClient` (`_call`/`ping`, тот же паттерн один клиент
на один вызов, а не долгоживущий объект). Новых записей в
`requirements.txt` в этой сессии нет вообще — меньше веса exe и меньше
риска сборки, чем предполагала исходная оценка, не больше.

**Ключ и модель — тот же путь, что у вебхука Bitrix24, вплоть до
ротации.** `llm_api_key` шифруется через `SecurityService.encrypt_secret`/
`decrypt_secret` и хранится в `app_settings`, `register_llm_rotation`
дословно повторяет `register_bitrix_rotation` (С6) — без него смена
мастер-пароля молча делала бы сохранённый ключ нечитаемым. `llm_enabled`
и `llm_model` — открытые настройки, не секреты, той же `get_setting`/
`set_setting` парой. `is_enabled(db, security)` — единственная точка
входа: `True` только когда включена галочка **и** ключ действительно
расшифровывается в непустую строку; `build_client()` — тот же гейт, но
сразу отдаёт готовый клиент или `None`, и это единственная функция,
которую вызывает любая кнопка на карточке лида и кнопка «Проверить
подключение» в Настройках — гейт не дублируется по местам вызова.

**Кнопка, не хук, не обязательное чтение при открытии карточки.**
Ни один код в этой сессии не запускает LLM-помощника сам — ни при
открытии карточки лида, ни при появлении новой заявки, ни по таймеру.
Это прямое следствие «работает как подсказка: ничего не пишется молча»:
единственный способ добавить хоть один сетевой запрос — явный клик по
одной из трёх кнопок на новой вкладке «Помощник». Отсюда же и то, что
у С9, в отличие от С6/С7, нет собственного сервиса с тик-циклом и нет
поля в `AppContext` — добавлять их было бы держать структуру ради
структуры: обслуживать здесь нечего, отправлять запрос повторно при
сбое сети тоже не нужно (в отличие от очереди Bitrix24, неудачная
попытка тут просто предлагает нажать кнопку ещё раз).

**Источник текста — уже отрисованная переписка, не отдельный запрос к
базе.** Все три кнопки («Извлечь поля», «Резюме», «Черновик») читают
`self.corr_view.toPlainText()` — тот самый текст, что уже показан на
вкладке «Переписка» этой же карточки, а не заново собранный список
сообщений. Это не только меньше кода: пользователь физически не может
не знать, что именно уйдёт в подсказку — оно уже перед ним на соседней
вкладке. Текст обрезается до последних 8000 символов ради ограничения
токенов; вкладка «Переписка» при этом продолжает показывать всё целиком.

**Извлечение полей не доверяет ответу модели вслепую.**
`parse_field_json()` снимает возможную ```` ```json ```` -ограду, парсит,
и оставляет только ключи из уже существующего `core.lead.
SCENARIO_LEAD_FIELDS` — того же списка, которым С3's сценарный движок
уже размечает «→ поле лида» для собранных вручную ответов, так что
LLM-извлечённое и сценарное поле оказываются на одной и той же земле.
Всё остальное (плохой JSON, не-объект, придуманный ключ, пустое
значение) отбрасывается, а не падает ошибкой — на экране это просто
означает «в этом поле ничего не нашлось», ровно то же самое, что и
«помощник ничего не предложил». На карточке те же восемь полей заранее
разложены в статичную форму (флажок + редактируемая строка на поле) —
извлечение только заполняет строки и включает флажки там, где что-то
нашлось; запись в `bot_leads` происходит только по отдельному клику
«Применить отмеченные» и только для отмеченных строк.

**Черновик ответа — буквально в `outbox_drafts`, тем же путём, что
холодное первое сообщение из С4.** «Сохранить как черновик» вызывает

наравне с «первое сообщение незнакомцу» из outbox.py. Бот, от чьего
имени уйдёт черновик, выбирается явно (комбобокс, по умолчанию — бот

`tg_user_id`/`telegram_id` лида или его контакта, тем же форматом, что
уже понимает `userbot_runner._resolve()`.

**Одна общая база, не общий класс-предок.** Ни один миксин не объявляет

**Проверка боем нашла реальный баг в `sqlite3` до того, как он попал в
код.** Черновик `upsert_mail_message()` брал id вставленной/обновлённой
строки из `cur.lastrowid` после `INSERT … ON CONFLICT DO UPDATE`.
Ручная проверка на живом `sqlite3.connect(':memory:')` показала: если
между первой вставкой строки A и апдейтом той же строки A через ON
CONFLICT произошла вставка другой строки B, `cur.lastrowid` после
UPDATE-ветки возвращает id **B**, а не A — SQLite обновляет
`last_insert_rowid()` только на пути реальной вставки, апдейт его не
трогает. При синхронизации почты, где апдейт одного письма в пачке
запросто соседствует со вставкой другого, это значило бы «письмо
сохранено под чужим id» — молча, без исключения. Ни один существующий
апсерт в кодовой базе (`upsert_chat`, `save_search_preset`,
`set_setting`) не полагается на `lastrowid` именно поэтому — не было
замечено при первом чтении их кода, замечено только когда пришлось
воспроизвести тот же приём и написать для него отдельную проверку.
Исправлено: `upsert_mail_message()` всегда перечитывает строку по
`(mailbox_id, folder, uid)`, никогда не доверяя `lastrowid`.

**Пароль ящика — не `register_setting_rotation()`, а отдельный модуль
по образцу токенов ботов.** Буквальная формулировка чек-листа («Пароль
через `SecurityService` + `register_setting_rotation()`») не учла
разницу форм: `register_setting_rotation()` (Р3) ротирует **один** ключ
`app_settings` (вебхук Bitrix, ключ LLM), а пароль ящика — это колонка
на **каждой** строке `mailbox`, потенциально нескольких. Ровно та же
развилка уже была решена в Р3 в пользу `bots/crypto.py`, когда токены
ботов не стали засовывать в общий хелпер. `integrations/mail/
credentials.py: register_mailbox_rotation()` — построчная ротация,
письмо в письмо повторяющая `register_bot_token_rotation()`.

**Синхронизация — не async, а блокирующий `imaplib` в экзекьюторе.**
У `imaplib` нет asyncio-клиента. `BitrixSyncService` мог просто
`await aiohttp`; здесь `MailService._sync_mailbox()` — обычная
синхронная функция, вызываемая из `tick()` через
`loop.run_in_executor(None, …)`, тем же приёмом, что уже применяет
`export_schedule_service.py` для тяжёлого экспорта. Инвариант «сетевой
обмен вне блокировки базы» проверен не описанием, а измерением:
тест поднимает поток, который 20 раз подряд пишет в базу, пока
`MailService` синхронизирует «медленный» (0.3 c на каждый FETCH)
поддельный ящик — фоновая работа с базой укладывается в 0.007–0.008 c
при тике почты в 0.7 c. Если бы блокировка держалась на время
«сети», это число было бы порядка секунд, не миллисекунд.

**Экран настроек — «Настройки → Почта» как отдельный пункт
`COMMON_ITEMS`, не карточка внутри `settings.py`.** Чек-лист не уточнял
форму; `settings.py` уже 1036+ строк и отмечен как «будет расти» ещё в
исходном плане, а список ящиков с проверкой подключения по объёму
сопоставим с тем, ради чего Bitrix24 в С7 получил собственный экран, а
не карточку. Прецедент применён напрямую: `ui/screens/mail_settings.py`
— отдельный файл, пункт навигации рядом с «Bitrix24». Когда П2 заведёт
полноценный блок «Почта» в переключателе слева, этот экран естественно
станет вкладкой настроек внутри него, а не будет вынесен второй раз.

приёмка П1 их не требует.** `imap_client.parse_full_message()` и

уровнями выше — `_safe_filename()` берёт `basename` по обоим
разделителям пути, не доверяя присланному имени.

**HTML-письмо без text/plain части получает `body_text` не `NULL`, а
через грубый `HTMLParser`-экстрактор.** Не рендеринг (инвариант П-3 не

для FTS-индекса: письмо-рассылка без обычного текста иначе было бы
ненаходимо по содержимому.

**Тесты.** `tests/test_mail_sync.py` — без сети, `FakeImapConnection`
эмулирует IMAP-ответы буквально в формате `imaplib` (включая тройку

mail.py` (+144 строки — цепочки, список, поиск, пометка «прочитано»),

**Участник собственного ящика — не участник цепочки.** Первый прогон
`test_mail_reading.py` дал ложное слияние: письмо от постороннего
человека с той же темой попало в чужую цепочку. Причина — адрес самого
ящика (`sales@company.ru`) фигурирует в *каждом* письме этого ящика
(как отправитель или как получатель), поэтому пересечение множеств
участников было тривиально истинным для любых двух писем с одинаковой
темой, независимо от того, кто на самом деле был вторым участником.
Исправлено на двух уровнях: `thread_participants(thread_id, exclude=None)`
в `mixins/mail.py` отбрасывает собственный (приведённый к нижнему
регистру) адрес ящика из возвращаемого множества; `_find_subject_thread()`
в `mail_service.py` вычисляет `own_address` по строке ящика и передаёт
его как `exclude=`, а также вычищает его из `sender_address`/
`to_addresses` нового письма перед тем, как отдать их в чистую
`find_subject_fallback_thread()`. Сама чистая функция в
`core/mail_thread.py` осталась в стороне от этого бага — участников ей
подают уже без примеси, что и держит её тестируемой без sqlite.

**Дедупликация «одно письмо на два ящика» — не сделана буквально, как
записано в чек-листе, по двум причинам.** Во-первых, схема `mail_thread`
уже спроектирована и смигрирована в П1 со скоупом на один ящик
(`mail_thread.mailbox_id NOT NULL`) — «одна цепочка с двумя метками»
означала бы единый inbox поверх нескольких ящиков, чего П1 не строил и
чек-лист П2 явно не заказывал отдельным пунктом. Экран этой сессии
поэтому показывает цепочки per-ящик+папка (левая колонка выбирает
именно эту пару) — тот же скоуп, что уже был в `list_mail_threads()`.
Во-вторых, предложенный чек-листом инструмент — `db/dedup.py:
fingerprint()` — на поверку не тот: это хэш **текста тела** для защиты
от почти-дублей при повторном сборе Telegram-сообщений, а «одно и то же
письмо» в почте уже имеет точный, стандартный идентификатор —
`Message-ID`, ровно то же поле, что и `_find_reference_thread()`
использует для склейки ответа с исходным письмом. Тот же принцип, что
Р3 уже применял к чек-листам: не подгонять реализацию под названный
хелпер, если он не подходит по форме, — здесь `fingerprint()` решал бы
другую задачу (почти-дубли), а не эту (точно то же письмо, увиденное
дважды). Итог: единого экрана «Входящие всех ящиков» в этой сессии нет;
если он понадобится позже, у него уже есть на что опереться —
`Message-ID`-совпадение между ящиками, а не текстовый отпечаток.

**Цветная метка ящика в списке цепочек — тоже не сделана, но по другой
причине.** Она имеет смысл в первую очередь в едином inbox, где на одном
экране вперемешку видны письма разных ящиков и метка — единственный
способ понять, откуда какое письмо. Здесь цепочки уже отфильтрованы
выбором в левой колонке («какой ящик и какая папка»), поэтому
неоднозначности, которую должна снимать метка, попросту не возникает
внутри одного списка. Оставлено как задел для будущего единого inbox,
если он появится, а не забыто.

**`imaplib` и кириллица в `SEARCH` — `self._encoding = 'ascii'`
зашит в стандартную библиотеку.** `client.search_uids()` сначала
собирал команду `SEARCH TEXT "запрос"` обычной Python-строкой;
`imaplib.IMAP4._command()` кодирует аргументы в ASCII по умолчанию и
падает на первом же кириллическом символе. Раз половина клиентских
писем — на русском, это не крайний случай, а обычный день. Исправлено
через `CHARSET UTF-8` в самой команде `SEARCH` плюс предварительное
кодирование поискового терма в `bytes` (`_quote_search_term()`) —
`imaplib` пропускает `bytes`-аргументы как есть, не пытаясь их
перекодировать.

**Поиск по телу письма ничего не находит, пока тело не запрошено явно
— это не баг, это П1-инвариант «тело по требованию», и тест сначала
его случайно нарушил.** Первая версия `test_mail_reading.py` ждала,
что `search_mail(mb, "2 тонны")` найдёт письмо сразу после обычной
синхронизации — но заголовки синхронизируются жадно, а `body_text`
остаётся `NULL`, пока кто-то не вызовет `fetch_body()` (реализовано ещё
в П1, экраном не использовалось до этой сессии). Переписано в две
части: сперва проверка, что поиск по телу до `fetch_body()` находит
пусто (документирует двухфазный забор как есть), потом — `fetch_body()`
и повторный поиск, который уже находит. Ложный красный тест стал
позитивной демонстрацией задуманного поведения вместо неверной
проверки.

**Блок «Почта» — четвёртый в `BLOCKS`, не карточка и не пункт
`COMMON_ITEMS`.** П1 сознательно держал «Ящики» в `COMMON_ITEMS` как
временное решение до тех пор, пока не появится «что-то ещё, кроме

тот же экран настроек П1, без переписывания, просто сменивший место в
навигации, ровно как было предсказано в журнале П1.

**Тесты.** `tests/test_mail_threads.py` — чистая логика сборки цепочки,
без sqlite и Qt. `tests/test_mail_reading.py` — цепочки поверх настоящего
конвейера синхронизации (через `_fake_imap.py`, вынесенный из
`test_mail_sync.py`), список цепочек и его агрегаты, чтение по порядку
дат, локальный FTS-поиск (включая двухфазность «тело по требованию»),
серверный поиск, пометка «прочитано» локально и её пуш на сервер. Полный
регресс — 36 тест-файлов (было 34, добавились `test_mail_threads.py` и

**Числа.** Новое: `core/mail_attachment_text.py` (160 строк — docx/xlsx,
без Qt), `ui/screens/mail/attachment_view.py` (376 строк —
`AttachmentViewerDialog`), `tests/test_mail_attachments.py` (283

её DDL), `db/migrations.py` (+47 строк), `db/mixins/mail.py` (+12

**Просмотр = индексация — один проход, а не отдельный конвейер
разбора.** Чтобы показать docx/xlsx/PDF, вьюер и так должен прочитать
их содержимое; извлечённый текст просто сохраняется тем же вызовом,
при первом открытии (`AttachmentViewerDialog._remember_text()`), вместо
фоновой задачи, которая бы парсила то же самое во второй раз. Прямое
следствие: вложение, которое никогда не открывали, не участвует в
поиске — тот же принцип «по требованию», что П1 ввёл для тела письма
(`fetch_body()`) и П2 явно продемонстрировал тестом. Не баг, а то же
самое решение, применённое второй раз.

**PDF-текст — через `QPdfDocument.getAllText()`, на GUI-потоке, а не
через `MailService.extract_attachment_text()`.** `QPdfDocument` —
Qt-объект; конструировать его на потоке экзекьютора (как `fetch_body()`
делает для остального) означало бы нарушить обычное для Qt требование
«графические объекты — с того потока, что создал `QApplication`».
Проверено не только чтением документации: собран настоящий
однострочный PDF через `QPdfWriter`+`QPainter` (без внешних
зависимостей — оба класса уже есть в `QtGui`), загружен обратно через
`QPdfDocument.load()`, и `getAllText(0).text()` вернул ровно тот же
текст посимвольно — round-trip, не предположение. docx/xlsx, наоборот,
идут через `run_blocking()` в `core/mail_attachment_text.py`, как и
всё остальное сетевое/блокирующее в этом модуле.

Round-trip подтвердился на Linux, но не на Windows-раннере CI: тот же
код (диалог строится без исключений — `QPdfDocument.load()`/
`getAllText()` честно отрабатывают) на Windows вернул из
`getAllText()` пустой текст для того же нарисованного через
`QPainter.drawText()` PDF — судя по всему, шрифт/шейпинг, которым
`QPdfWriter` рисует текст, отличается по платформе, и встроенный
ToUnicode CMap не всегда получается у него настолько же полным, как на
Linux. Тест смягчён: жёсткая проверка того, что диалог строится и
`set_attachment_extracted_text()` сохраняет то, что ему передали
(проверено на docx, где извлечение — свой код, не зависящий от системных
шрифтов), плюс мягкая, информационная проверка результата на PDF —
без падения теста, если конкретная платформа не смогла вытащить текст
из конкретно этого рукописного файла. Настоящие письма приходят как
PDF от Word/Adobe/сканеров с полноценными шрифтовыми таблицами, а не
нарисованные `QPainter` на лету, так что это в первую очередь ограничение
методологии теста, а не подтверждённая проблема с реальными вложениями
— но и не то, что эта сессия смогла проверить на Windows напрямую.

**Ручной разбор `QPdfBookmarkModel`/`QPdfSearchModel`/`QPdfPageNavigator`
API — интроспекцией, не по памяти.** У PySide6's QtPdf нет типовых
примеров в этой кодовой базе (первое использование PDF вообще); прежде
чем писать `_build_pdf()`, каждый метод (`getAllText`, `jump`,
`Role.Page`, `Error.IncorrectPassword`) проверен через `dir()`/`help()`
на реальных объектах — один черновой вызов (`view.pageNavigator().jump(
int(page), Qt.QPointF if False else …)`) уцелел от этой разведки и был
пойман и вычищен только при повторном чтении файла, не при тестовом
прогоне: `tests/test_mail_attachments.py` не проверял именно эту
ветку (клик по оглавлению) до финальной проверки. Из-за этого
`AttachmentViewerDialog` в конце сессии собран для всех шести вариантов
офскрин (PDF/xlsx/docx/PNG/`.doc`/отсутствующий файл) — единственный
способ поймать опечатку в Qt-вызове, которую не ловит ничего, кроме
реальной конструкции виджета (тот же урок, что смоук-тест экранов уже
преподавал в С1–Р7).

**Сетка Excel: `max_col`, переданный `iter_rows()` без разбора, красил
таблицу в 200 пустых столбцов.** Первая версия `read_xlsx_grid()` жёстко
передавала `max_col=MAX_XLSX_COLS_PER_SHEET`, а `openpyxl` дополняет
**каждую** строку до этой ширины пустыми ячейками — трёхколоночный
прайс превращался в таблицу шириной 200 столбцов, 197 из которых
пустые. Проверено printʼом фактической сетки прямо в интерпретаторе
до того, как код попал в вьюер; исправлено — `col_cap = min(ws.max_column
or 1, MAX_XLSX_COLS_PER_SHEET)`, предел сужает реальную ширину листа,
а не подменяет её.

**Заморозка шапки — нативным горизонтальным заголовком `QTableWidget`,
не отдельным виджетом.** Чек-лист просил «заморозку шапки» отдельным
пунктом, как если бы это была своя техника; Qt уже держит
горизонтальный заголовок таблицы приклеенным сверху при вертикальной
прокрутке — `read_xlsx_grid()` отдаёт первую строку листа отдельно,
`_build_xlsx()` кладёт её в `setHorizontalHeaderLabels()`, а не в тело
таблицы, и требование выполняется тем, что Qt и так умеет, без кода
ради кода.

**Дедупликация «файловых бомб» — три отдельных предела, не один.**
Чек-лист говорил «предел на распакованный размер и число листов»;
реализовано три: `MAX_ZIP_UNCOMPRESSED` (общий распакованный размер
архива), `MAX_ZIP_MEMBERS` (число файлов внутри архива — «число листов»
из чек-листа плюс общий случай для .docx, у которого «листов» в
Excel-смысле нет), `MAX_XLSX_SHEETS`/`MAX_XLSX_ROWS_PER_SHEET` (число
листов и строк уже внутри книги). Первые два проверяются по
центральному каталогу zip — без распаковки; оба протестированы через
временное занижение предела на обычном маленьком файле (не через
настоящий гигабайтный архив, которого в тестовом окружении быть не
должно) — так же, как send_limits тестируют пороги без реального часа
ожидания.

**П-4 в трёх местах, не одном.** Просмотр вместо запуска —
`AttachmentViewerDialog` никогда не вызывает файл, только показывает
его или открывает во внешнем приложении по явному клику. Полное имя с
расширением — сохраняется как есть от `_safe_filename()` (П1), нигде не
усекается. Маркировка исполняемых расширений — новая
`is_executable_attachment()` в `ui/screens/mail/__init__.py`, проверяет
**все** точечные суффиксы, а не последний, так что `Заявка.pdf.exe`
помечается ровно как чек-лист и просил. Разбор без формул/макросов/
внешних ссылок — уже верно по построению: `openpyxl` с `data_only=True`
читает закэшированные значения формул, не пересчитывает их, а ручной
`xml.etree`-разбор docx вообще не видит ничего, кроме текстовых узлов.

**Не сделано, сознательно.**
- Пароль PDF — код (`QPdfDocument.Error.IncorrectPassword` → диалог →
  `setPassword()` → повторный `load()`) не покрыт автотестом:
  сконструировать корректно зашифрованный PDF без внешней библиотеки
  (`QPdfWriter` шифрование не пишет) — отдельная задача, несоразмерная
  своей ценности здесь. Путь короткий и линейный, риск невысокий;
  дисклеймер честнее, чем обход через фиктивный тест.
- Перетаскивание вложения в проводник — не сделано; «сохранить как…»
  (по одному) и «сохранить все» (когда вложений больше одного, в
  панели письма) закрывают тот же сценарий без `QDrag`/`QMimeData`
  urls, которые чек-лист не называл отдельно, а лишь предполагал
  словом «перетаскивание».
