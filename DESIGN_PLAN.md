# Карта переверстки ChatGrab — «Плотный рефреш»

Рабочий документ для визуального редизайна приложения, отдельный от `PLAN.md`
(там — функциональные сессии С/Р/П, здесь — только слой представления). Источник
истины по дизайну — два файла в `design/`:

- `design/design-brief.md` — полное техзадание: токены, компоненты, экран за
  экраном, анимации, пустые состояния, инварианты вывода. **Читай его целиком
  перед началом любой сессии Д — здесь только план и решения по спорным
  местам, не дублирование содержимого.**
- `design/mockup-1a.html` — целевой визуальный референс (8 экранов, которые
  бриф расписывает буквально). Открой в браузере, сверяйся глазами: цвета,
  отступы, шрифты, порядок элементов, hover-состояния.

Обновляется в конце каждой сессии — статусы и журнал внизу, как в `PLAN.md`.

---

## Как начинать сессию

Скажите одну фразу:

> Прочитай DESIGN_PLAN.md, начинаем сессию Д<N>.

Сверю состояние репозитория с этим файлом и с `design/design-brief.md`, назову,
что осталось от прошлого раза, и начну. В конце сессии — обновлю статусы,
скриншот/офскрин-проверку и журнал.

Порядок Д4–Д10 не догма — это независимые блоки экранов, можно попросить
любой раньше. Д1→Д2→Д3 и Д11 — жёсткая последовательность (фундамент и
финальная сверка).

## Решённые развилки (не переспрашивать заново)

Бриф (`design/design-brief.md`) сам написан против **более старой** версии
приложения — плоский сайдбар из 8 пунктов без блоков, без блока «Лиды», без
всего блока «Почта» (П1–П10 целиком отсутствуют в брифе). Прежде чем писать
этот план, я сверил бриф с текущим кодом и получил два решения:

1. **Структура навигации не меняется.** Сайдбар остаётся 4-блочным
   переключателем (Сбор / Боты / Лиды / Почта, `main_window.py: BLOCKS` /
   `NAV_BY_BLOCK`) со всеми текущими 26 пунктами. Плоский сайдбар макета —
   это референс **языка оформления** (цвета состояний, hover/active, стиль
   иконок), а не буквальный список пунктов для копирования. Ничего в
   `BLOCKS`/`NAV_BY_BLOCK`/`COMMON_ITEMS`/сигнатурах `navigate()` не меняется.
2. **Дизайн распространяется на все 44 экрана/диалога**, не только на ~8,
   расписанных в брифе буквально (§4.1–4.8). Для экранов без прямого
   соответствия в брифе (Наблюдение, Направления, Bitrix24, весь блок «Лиды»,
   весь блок «Почта», диалоги карточек лида, виджет рабочего стола, трей) —
   применяется тот же токены/компоненты (§2–§3 брифа), рисунок беру по
   аналогии с ближайшим расписанным экраном того же типа (список+карточка,
   таблица, форма настроек, лог) и отмечаю решение в журнале сессии.

Экран «Обзор» из брифа (§4.1) соответствует нынешнему `today.py` («Сегодня») —
не отдельный новый экран, а редизайн существующего с поправкой на то, что
`today.py` реально показывает сейчас (расхождения — на усмотрение сессии Д4,
с пометкой в журнале).

## Границы: что меняем, что нет

Как в брифе (§1), без исключений:

**Меняем только слой представления:** `chatgrab/ui/theme.py`,
`chatgrab/ui/main_window.py` (только сайдбар/шапка, не `BLOCKS`/`NAV_BY_BLOCK`),
`chatgrab/ui/widgets.py`, `chatgrab/ui/widget_window.py`, `chatgrab/ui/tray.py`,
`chatgrab/ui/screens/**/*.py` (только вёрстка).

**Не трогаем** (ни сигнатуры, ни поведение): `chatgrab/db/*`, `chatgrab/telegram/*`,
`chatgrab/services/*`, `chatgrab/bots/*` — кроме нового **read-only** запроса
для отображения (тогда метод добавляется в `db/mixins/*.py`, существующие не
меняются). Все сигналы/таймеры/навигация (`on_show(**kwargs)`,
`navigate("collect", chat_id=...)` и т. п.) сохраняются буквально.

Инварианты безопасности вывода из брифа §8 (`Qt.PlainText` для текста из
Telegram/почты, QSS вместо HTML-обёрток в f-строках, `QDesktopServices` для
файлов, явные тёмные фон/текст у всех `QAbstractItemView`/`QDialog`/
`QScrollArea`) — держатся в каждой сессии Д, не только в финальной проверке.

цифр/дат/id/логов), `build_qss()` переписывается под новые токены.

**Зависит от:** —

- [x] Все цвета §2 брифа как константы в `theme.py`, никаких хардкод-хексов
      нигде дальше по плану
- [x] Геометрия §2 (радиусы карточки/кнопки/плашки, паддинги, тени) — именованные
      константы, не магические числа в каждом экране
- [x] `build_qss()` переписан: карточки, поля ввода, кнопки (5 типов из §3.3),
      скроллбар, `QAbstractItemView`/`QDialog`/`QScrollArea` — тёмный фон явно
      (инвариант §8, не потерять существующие комментарии-обоснования)
- [x] Фон рабочей области — сетка 32×32px (бриф §2 «Фон рабочей области»):
      либо через QSS/`background-image`-эквивалент, либо `paintEvent` контейнера
- [x] Существующий код всё ещё запускается и рендерится (даже если визуально
      «переходное» состояние) — ничего не падает на старте
- [x] `tests/test_stylesheet_leaks.py` (или его наследник) зелёный — QSS не течёт
      между несвязанными виджетами

**Приёмка:** новая палитра и геометрия существуют как константы, `build_qss()`

## Журнал

### Д1 — готова

`chatgrab/ui/theme.py` переписан целиком: все цвета/оверлеи §2 брифа как
именованные константы, включая новые (`SURFACE_INPUT`, `DIVIDER_SOFT`,
`BORDER_HOVER`, `TEXT_LOG`, `ACCENT_FILL`/`_FILL_HOV`/`_ON_FILL`, `WARN_FG`,
`OVERLAY_ACCENT_WEAK`/`_ACTIVE`, `HOVER_NEUTRAL`, `CHECKBOX_OFF_BG`,
`CARD_INNER_GLINT`).

**Найдено по дороге:** старые `BAD`/`BAD_FG` (`#C98A9A`/`#F0C6CF`) не
совпадали ни с брифом (`#C85A6E`/`#E9B3BF`), ни с уже верными значениями в
собственном же `STATUS_STYLES["error"]` (`dot`/`fg`) — два источника правды
для одного и того же красного разошлись в этом же файле. Приведено к
брифу. Проверено `grep` по всему `chatgrab/`: ни `BAD`, ни `BAD_FG`, ни
`GOOD_BG`/`WARN_BG` нигде не импортируются напрямую за пределами
`theme.py` — правка безопасна, менять было нечего дальше по коду.

**Кнопки:** primary стала залитой (`ACCENT_FILL`/`ACCENT_ON_FILL`), а не
обводкой — «главное отличие» по формулировке самого брифа §3.3. Добавлен
пятый тип, `icon` (24×24 иконка-кнопка, по умолчанию `TEXT_FAINT`,
наведение — красный), которым пока никто не пользуется — существующие
экраны используют `danger` для текстовых кнопок удаления, это разные
роли, `icon` подключит Д2/более поздние сессии.

**Тени — вне QSS.** Qt Style Sheets не поддерживают `box-shadow` вообще
(ни обычный, ни `inset`) — тень кнопки и блик внутри карточки из брифа
физически не выразить в `build_qss()`. Оставлены как обычные Python-
константы (`SHADOW_BUTTON_PRIMARY`, `SHADOW_TILE_HOVER`, `CARD_INNER_GLINT`)
для применения через `QGraphicsDropShadowEffect`/собственный `paintEvent`
в Д2 (виджет `Card`) — не забыто, просто не то место.

**Сетка фона** — `theme.draw_grid_background(painter, rect)`, чистая
функция рисования, не привязанная ни к какому виджету (импорт `QColor` —
внутри функции, не на уровне модуля, чтобы весь остальной файл оставался
импортируемым без поднятого `QApplication`). Не подключена к `QWidget#root`
— тот виджет строится в `main_window.py`, это файл Д3, не Д1; проговорено
явно в докстринге функции, чтобы Д3 не забыла.

**Кикер — теперь моно**, ключевая часть нового языка (брифа §2 «Технический
шрифт»): `Consolas` с обычным `sans` fallback. Текст кикеров по-прежнему
должен приходить в верхнем регистре из вызывающего кода — не полагаюсь на
CSS `text-transform` для кириллицы между платформами (тот же выбор, что уже
стоял в докстрингах остальных `label()`-хелперов).

Полный регресс — 50 тест-файлов + смоук, зелёные без единой правки самих
тестов. `test_stylesheet_leaks.py` (реальный, пиксельный тест на настоящем
`MainWindow`) подтвердил: выбранное/невыбранное состояние блока-
переключателя, пункта меню и чипа всё ещё визуально различимо после смены
токенов — не просто «не упало», а действительно то же поведение с новым
цветом.

Не сделано, сознательно: ни один экран не тронут (это Д4+), TabletCheckBox/
ToggleSwitch-анимация/Sparkline/MetricsBar/LogPanel — Д2, сайдбар и подключение
сетки фона — Д3. Часть новых токенов (мелкие типографические роли из
таблицы §2 — «Название чата в плитке», «Текст сообщения в поиске» и т. п.)
не получили отдельных QSS-классов в этой сессии — это решения по вёрстке
конкретных экранов, не токены уровня темы, будут заведены по месту в Д4+.

Состояние: приложение стартует и работает как раньше, визуально уже
частично «новое» (кнопки, инпуты, скроллбар, кикеры) там, где экраны
используют существующие QSS-классы — не финальный вид ни одного экрана, а
ожидаемое переходное состояние перед Д2/Д3.

conclusion `success`) — полный регресс подтверждён не только локально, но
